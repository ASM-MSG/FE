# MSG-431: [모바일] 내 영상 관리 — 공개 범위 전환·삭제 확인·신고

## 기획 요약

도감 갤러리의 내 영상 카드에 더보기(⋯)를 얹어, 하단 액션시트로 **공개 범위 전환(전체 공개/나만 보기)**과 **영상 삭제(확인 다이얼로그 경유)**를 제공한다. 웹 MSG-411이 Radix 드롭다운으로 한 것을 모바일 관례인 하단 시트로 옮기며, 파생 로직(`video-menu`)은 웹에서 포팅하고 parity로 드리프트를 고정한다. 확장 지점은 MSG-425가 `gallery-video-card.tsx`에 예고해 둔 대로 `VideoCard`의 `overlay` prop이며, `packages/ui-native`는 무수정이다(ActionSheet가 이미 `selected` ✓ 행·섹션 라벨·구분선을 갖고 있고, SOURCE 주석이 이 티켓의 Figma 노드 `14856:510`을 그대로 가리킨다).

신고는 **모바일에 실 videoId를 가진 타인 영상 화면이 없어** 이 티켓에서 배선할 곳이 없다 — 아래 질문 Q4에서 결정한다.

## 추정 및 질문

> 전부 승인 게이트에서 답이 필요하다. Q1·Q4는 구현 방향을 가른다.

- **Q1 (필수) — 현재 공개 범위를 무엇으로 읽는가.** `GET /api/collections/videos`의 `RegionVideoResponseDto`에 **`visibility` 필드가 없다**(필드 8개 전수 확인). 웹은 더보기 메뉴를 열 때 `GET /api/videos/{videoId}/playback`을 쳐서 `visibility`를 얻는다. 그런데 그 엔드포인트의 명세 주석은 `viewCount: 조회수 (이번 조회 증가 전 스냅샷)` — **더보기를 여는 것만으로 조회수가 오른다**(웹도 지금 같은 부작용을 안고 있다). 선택지:
  - **(a) 권장 — 웹과 동일하게 `getPlayback`으로 보강**하고, 명세 환류(목록 응답에 `visibility` 추가 요청)를 지라에 남긴다. 플랫폼 간 동작이 갈리지 않는다
  - (b) 시트를 열어도 ✓를 표시하지 않고 선택만 받는다 — 티켓 [동작 요구]("현재 상태에 체크가 표시된다") 위반
  - (c) 항상 "전체 공개"에 ✓ (기본값 가정) — 잘못된 정보를 보여줄 수 있어 비권장

## 신고 배선 결정 (Q4 대체 — 스펙 본문의 "제외" 판정을 뒤집는다)

**근거가 된 실측**
- `GET /api/grids/{gridId}/videos`(`getGridGlobalVideos`)는 **본인·타인 포함 공개·READY 영상**을 `videoId: number` + `nickname`으로 내려준다. 모바일에서 실 videoId를 가진 타인 영상을 얻을 수 있는 **유일한 경로**다
- `GET /api/grids/{gridId}/my-videos`(`getGridVideos`)는 그 격자의 **내 영상**만 준다 → 두 목록의 `videoId` 교집합으로 **소유 판정(`mine`)이 정확히 계산된다**. 닉네임 문자열 비교 같은 추정이 필요 없다
- 모바일 라우트 cellId `cell-{col}-{row}`는 서버 `gridId`로 **결정적 변환이 가능하다** — `grid.ts:37` 주석이 `col = 서버 gridX`, `row = 서버 gridY`를 명시하고 `gridId`는 `"{grid_y}_{grid_x}"`다. 즉 `gridId = "{row}_{col}"`
- 병렬 웨이브 3 대조: MSG-427은 `features/map-home`(테마 시트), MSG-428은 클러스터 마커, MSG-430은 도감 뱃지·기록이며 **MSG-430 [제외 범위]가 "영상 공개 범위·삭제·신고는 MSG-431"이라고 명시**한다. `features/grid-detail`을 건드리는 웨이브 3 티켓은 없다

**결정**
1. `features/grid-detail`의 "이 격자의 영상" 목록을 **mock → 실 API로 교체**한다(`getGridGlobalVideos` + `getGridVideos` 교집합으로 `mine` 판정). 나머지 mock(통계·지도·미리보기)은 **손대지 않는다** — 이 티켓의 목적은 신고 배선이지 격자 상세 실연동이 아니다. 남은 mock은 리포트에 명시하고 환류한다
2. 영상 **행마다** ⋯ 를 얹고, `features/video-actions`의 **같은 `VideoMoreSheet`를 재사용**한다 — `mine=true`면 공개 범위 2행 + 영상 삭제, `mine=false`면 신고하기. 도감 갤러리와 시트 구현이 하나다
3. `report-modal.tsx`의 제출을 **실 `POST /api/videos/{videoId}/reports`에 연결**하고, 중복 신고(409 / developCode 11409)에 안내를 띄운다. 웹 `report` 모델을 포팅하고 parity 테스트를 동반한다
4. 화면 상단의 기존 ⋯(격자 단위 수정/삭제/신고)는 **영상 단위 메뉴와 의미가 겹치므로 정리**한다 — 격자에 대한 "영상 삭제/신고"는 대상이 불분명한 mock 잔재다. 처리 방향은 구현 시 판정하고 리포트에 근거를 남긴다
5. `hasCellVideos`(mock 기반 진입 게이트, **`features/grid-detail` 소유**)를 실데이터 기준으로 바꾼다. **`map-home-screen.tsx`는 수정하지 않는다** — 함수 이름·시그니처를 유지해 호출부 diff를 0으로 두면 MSG-427·428의 `map-home-screen.tsx` 리베이스와 충돌하지 않는다

## 테스트가 잡은 것

- **회귀(검증 단계)**: 신고 모달 `submit`이 `reset()`을 잃어 **영상 A를 신고한 사유가 영상 B 신고 모달에 선택된 채 남고 [신고 제출]이 즉시 활성**되는 오신고 경로. 기존 테스트 576건이 전부 통과한 채로 통과했다 — 상태가 컴포넌트 안에 있어 단정 지점이 없었던 것이 원인이고, 리듀서 분리 + 회귀 주입 RED 실행으로 고정
- 같은 부류 2건 추가 발견: `grid-detail-screen`의 `reportFailure`(A의 실패 문구가 B의 모달에 표시)·`video-actions-menu`의 `deleteMessage`

**재작업 2회차 (커밋 전 codex 리뷰 3건 — 전건 동의, 반박 없음)**
- ① 삭제 확인 다이얼로그 **중복 DELETE**: `mutationKey`를 가진 옵션이 `setVisibility` 하나뿐이라 삭제·신고는 가드할 수단 자체가 없었다(비대칭 = 설계가 아니라 누락). 3종 전부에 키를 부여하고 `guardMutate` 하나로 통일
- ①의 후반부 **실패 문구 잔존**: 삭제 성공 닫힘(`onDeleted`)이 `deleteMessage`를 비우지 않아, 3초 자동 소멸 전에 다시 열면 지난 실패가 남았다. 1회차의 `closeReport`와 같은 방식으로 `closeDelete`를 만들어 성공·취소가 같은 경로를 타게 함
- ② 신고 제출 **중복 POST**: 둘째 요청이 서버 409(`11409`)를 받아 "신고가 접수되었어요" 위에 "이미 신고한 영상이에요"가 덮이는 모순 화면
- ③ 목록 **재시도 편측**: `retry: global.isError ? globalStatus.retry : mineStatus.retry` — 둘 다 실패면 global만 재조회돼 성공해도 화면이 계속 실패. 웹 정본 대조 후 양쪽 refetch로 교정
- 3건 모두 **회귀를 코드에 되돌려 주입해 RED를 실행으로 확인**했다(`expected [ 1, +0 ] to deeply equal [ 1, 1 ]` 등 — 리뷰가 기술한 증상과 일치). 상세 출력은 `_workspace/MSG-431/02_build_report.md` 재작업 2회차 §5-2
- nose 신규 패밀리 2건 중 **테스트 실중복 1건은 baseline 등재가 아니라 코드로 제거**(헬퍼 공유), 웹↔모바일 포팅 1건만 등재
