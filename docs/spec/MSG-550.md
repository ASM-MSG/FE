# MSG-550: 반려 재신청 — 위저드 수정 모드 프리필 · 반려 사유 병기 · PATCH 재제출

## 기획 요약

반려된 신청을 반려 사유를 보면서 고쳐 다시 제출하는 경로. `/org/submissions/:submissionId/edit`(MSG-541 선등록, 위저드 페이지 공용 라우트)에서 등록 위저드를 **수정 모드**로 열어 기존 제출값(기본 정보·대표 이미지·위치 영역)을 프리필하고, 반려 항목·사유를 병기한 채 고쳐 `PATCH /api/org/event-submissions/{submissionId}`로 재제출한다. 성공 시 상태가 심사 중으로 복귀하고 내 신청 목록으로 이동하며 목록·상세·홈 카운트가 갱신된다. 유형은 수정 모드에서 변경 불가. 승인 건 수정은 제외 범위(반려 건만 — 티켓 확정, A안 2026-09-01).

## 전제 — MSG-548 순차 진행 (스펙에 명시하라는 지시 사항)

이 티켓은 **MSG-548(최종 검토·제출) 머지 후 순차 진행**된다. `_workspace/MSG-548/01_spec.md`·`docs/spec/MSG-548.md`는 **아직 존재하지 않아**(2026-09-04 실측) 접점은 인터페이스 가정으로 적는다 — **구현 착수 시 develop의 548 산출물을 실측해 파일명·배선을 확정하고, 어긋나면 스펙 이슈로 올린다**:

- 548이 만들 것(가정): review 스텝 실구현(`WizardStepSwitch` review case 교체) + POST 제출 경로(`submitMutation` + `toCreateDraft` 완성 — 스토어 주석 실측 근거) + 제출 실패 에러 표면 + 성공 후 이동 규칙.
- **접점 = 제출 mutation 분기**: review 스텝의 제출 CTA가 스토어 mode로 갈라진다 — create → `POST submit`(EventSubmissionCreateRequestDto, 548 소유) / edit → `PATCH resubmit`(EventSubmissionUpdateRequestDto, 이 티켓 소유). 요청 본문 조립도 갈라진다(`toCreateDraft` vs 신규 `toUpdateDraft`). 실패 안내·재시도 UX는 548의 규칙을 그대로 재사용한다(티켓: "제출 실패 시 처리도 신규 제출과 동일한 규칙").
- 548이 review 스텝에서 이 분기를 미리 만들어 두지 않는 한, 이 티켓이 review 스텝 CTA 배선을 mode 분기로 확장한다(548 산출물 파일 수정 — 순차라 충돌 없음).

## 코드베이스·API 실측 (스펙의 전제 — 전부 이 세션 실측)

**PATCH 계약 (`resubmit` — sdk.gen.ts, 재생성 금지)**
- `PATCH /api/org/event-submissions/{submissionId}`, body `EventSubmissionUpdateRequestDto`. API 주석: "**반려된 신청만** 수정할 수 있고, 재제출하면 상태가 심사 중으로 돌아간다(신청 번호는 그대로). **부분 수정이 아니라 전체 교체**이고 **등록 유형은 바꿀 수 없다**."
- **Create와의 필드 차이(실측)**: `type` 없음 · `parentOccurrenceId` 없음("부모 이벤트는 재제출로 바꿀 수 없어 이 요청에 필드가 없다" — DTO 주석) · `imageS3Key?` **생략/null이면 기존 이미지 유지**, 새 pending 키면 교체 · `locations?` "통째로 갈아끼우고 대표 격자를 전부 재계산". 나머지(title·organizerName·startsOn·endsOn·유형 전용 3필드 optional·description)는 Create와 동일. 응답은 submit과 같은 `ApiResponseDtoEventSubmissionSubmitResponseDto`. 생성 옵션 `resubmitMutation` 존재.
- `endsOn` 오늘 이전 13433은 PATCH에도 명시 — 기존 `periodIssueMessage` 선반영이 그대로 유효.

**프리필 재료 (`getSubmission` 상세 DTO)**
- `EventSubmissionDetailResponseDto`: 공통 5필드 + 유형 전용 3필드(`| null`, 해당 유형만 값) + `parentEvent {occurrenceId, name} | null`(EVENT만) + `imageUrl`(presigned GET) + `locations[]`(order 오름차순, **`areaRects`는 "제출 원본 사각형 — 재제출 폼 프리필 재료라 보낸 그대로"** — DTO 주석, `cellCount` 최대 81은 위치당) + `rejection {reasonCodes[], reasonText} | null`(REJECTED만) + `history[]` + `updatedAt`. `type`·`status`는 **plain string**(미지 값 가드 필요).
- 조회 훅 `useSubmissionDetailQuery(submissionId: number | null)`(features/org-submissions — null 미발사·`detail/isPending/isError/retry`)가 재사용 가능(MSG-549 "신규 훅 0" 선례). id 파싱은 `parseSubmissionId`(submission-detail-view) 재사용.

**위저드 확장점 (MSG-546·547 머지분)**
- `submission-wizard-store.ts` 확장점 주석: "MSG-550: `mode: "create" | "edit"` + 서버 신청 상세로 초기값을 채우는 hydrate 액션". 비영속 결정 사유도 550과의 오염 방지("이전 작성분이 남의 신청서로 새는 위험"). `areaRects`는 **위치 1개분 슬롯**(547 — 다중 위치 UX는 제외 범위였음).
- `WizardStepSwitch` 주석: "수정 모드는 스텝 구성을 그대로 쓰고 스토어에 mode·초기값을 얹는다 — **이 스위치의 분기는 늘지 않는다**."
- `OrgSubmissionWizardPage` 주석: edit 라우트가 이 페이지를 계속 렌더, "수정 모드 동작은 그 티켓이 스토어 mode 슬롯에 얹는다". 마운트 reset + 언마운트 blob 해제→reset.
- **blob: 가드 안전(실측)**: `pages/org/ui/preview-url.ts`의 `revokeBlobPreviewUrl`은 `blob:` 스킴만 해제한다 — 주석에 "MSG-550 수정 모드가 hydrate할 서버 이미지 URL(https:)을 건드리면 안 된다"고 이미 설계돼 있어 `previewUrl = imageUrl` hydrate가 안전하다.
- `isBasicStepComplete`는 `imageS3Key !== null`을 요구한다 — 수정 모드의 "기존 이미지 유지"(s3Key 없음)가 이대로면 스텝을 못 벗어난다 → 판정 확장 필요(구현 계획).
- `isSubmissionDirty`는 "빈 값 대비" 판정이다 — hydrate 직후 무조건 dirty가 되어 이탈 경고가 항상 뜬다 → 수정 모드 판정 확장 필요(질문 2).

**진입 버튼·무효화 대상 (기존재)**
- 진입로 2곳 기존재(MSG-549): 목록 반려 행 "수정 후 재신청"·반려 상세 CTA "수정 후 재제출" → `CONSOLE_ROUTES.orgSubmissionEdit`. **홈 요약 카드는 "상세 보기"만 있다(실측)** — 티켓의 "(또는 홈 요약 카드)"는 상세 경유로 충족, 홈 카드 버튼 신설 없음(추정 7).
- **홈 카운트 = `getMySubmissions` 응답 파생**(OrgHomePage 실측 — 별도 카운트 API 없음). 따라서 재제출 후 무효화 대상은 `getMySubmissionsOptions().queryKey`(목록+홈 카운트+홈 대표 카드) + `getSubmissionOptions({path:{submissionId}}).queryKey`(상세 — 홈 반려 요약 카드의 상세 조회와 캐시 공유) 2개로 전부 커버된다.
- 브랜치: `*MSG-550*` 로컬·리모트 모두 없음(실측) — 신규 생성.

2. **dirty 기준선** — 채택: hydrate 스냅숏 대비 **필드별** 비교. 기각: `JSON.stringify` 비교 — 서버 `areaRects`의 키 순서가 위저드 산출물과 달라 **같은 영역을 변경으로 오판**한다(테스트로 고정). 기각: 수정 모드 항상 경고(승인 확정안 (b)) — 사유만 확인하고 나가는 동선이 매번 confirm.
3. **"기존 이미지 유지" 표현** — 채택: `image.keptPreviewUrl`(서버 URL) 슬롯. 기각: `status: "kept"` — 유지 상태는 업로드 진행 상태와 **직교**하는데 한 축에 넣으면 "실패 + 유지"가 배타가 된다. URL을 들고 있으면 실패 복원 지점(추정 5)이 공짜로 생긴다.
4. **잠긴 스텝 렌더** — 채택: `<span>`. 기각: `onSelect` no-op 가드 — 포커스·클릭되는 죽은 버튼이 키보드 사용자에게 거짓 어포던스.
5. **`toUpdateRequest` 명명·소속** — 스펙은 `toUpdateDraft`/`submission-form.ts`를 지정했으나 **`toUpdateRequest`/신규 `submission-edit.ts`**로 갔다. 이 레포에서 `…Draft`는 부분형(`Partial<DTO>`)을 뜻하고(`toCreateDraft` 실재) 완전형 관문은 `…Request`(`toCreateRequest`)다 — 이름을 뒤집으면 계약이 뒤집힌다. 소속은 `submission-form.ts`가 유형별 폼 설정 3벌 + POST 계약의 정본이라 계약 축이 다른 3함수를 분리했다(유형 3벌 설정·필수값 판정은 import 위임 — 정본 중복 0).
6. **스토어 `mode`** — 546 주석은 상태를 예고했으나 `submissionWizardMode(state)` **파생**으로 이행. `editContext`가 곧 수정 모드의 근거라 별도 상태는 어긋날 자리(reset 누락 시 mode만 잔류)를 만든다.
7. **접수 Toast 미탑재** — AC 6이 요구하지 않고, 재제출은 신청 번호가 그대로라 목록의 "번호당 1회" ref 가드(548에서 무한 렌더를 냈던 경로)에 재신청 케이스를 얹으면 얻는 것 없이 위험만 는다.
8. **nose 4가족** — 로딩 스켈레톤 1가족 **추출**(prod 공유 뷰) + 스모크 내부 반복 실축소 + QueryClient 팩토리 인라인화(가족 소멸) + per-scenario 셋업 등재. `--write-baseline` 전면 재작성은 **기각 — 실행해 보니 타 티켓 등재분을 4216줄 삭제**해서 해당 가족만 수술적으로 병합했다(최종 +167/-4, 삭제 4줄은 전부 줄번호 필드).
