# MSG-465: [하네스] claude-review 완주 검증 오탐 해소 — 요약 마커 판정 방식 개선

## 기획 요약

`.github/workflows/claude-review.yml`의 "Verify review summary was posted" 스텝(현재 80~92행)이
리뷰가 정상 완주해도 실패로 표시한다(PR #89 `af67beb` 실측 — 봇이 요약을 진행 코멘트에 이어
붙이며 SHA 마커를 생략). 판정이 봇의 그때그때 코멘트 작성 방식에 좌우되는 것이 원인이다.
판정 근거를 봇 행동에서 분리하되, MSG-403이 세운 원래 목적 — 산출물 없이 종료한 실행은
여전히 실패 — 은 유지한다. 대상은 워크플로 파일 단독, 앱 코드 무변경.

## 사전 조사 결과 (방향 2 실현 가능성 — 스펙의 근거)

사용자 지시대로 **[검토 가능한 방향] 2번(execution output 판정)의 스텝 간 전달 가능성을 먼저
실증**했다. 결론: **가능하다.**

1. **`outputs.execution_file`은 액션의 공식 출력이다** — `anthropics/claude-code-action` 저장소
   `action.yml`의 outputs 선언에서 확인:
   `execution_file: "Path to the Claude Code execution output file"`.
2. **파일은 `$RUNNER_TEMP/claude-execution-output.json`에 쓰인다** —
   `base-action/src/execution-file.ts` 소스 실측 (`EXECUTION_FILENAME = "claude-execution-output.json"`,
   `join(process.env.RUNNER_TEMP, ...)`, `core.setOutput("execution_file", ...)`).
   `RUNNER_TEMP`은 잡(job) 수명 동안 유지되므로 **같은 잡의 후속 스텝이 경로를 받아 읽을 수
   있다.** 액션 스텝에 `id`를 부여하고 `${{ steps.<id>.outputs.execution_file }}`로 참조하면 된다.
3. **파일 내용은 SDK 메시지 전체 배열이다** — `base-action/src/run-claude-sdk.ts` 실측: 모든
   `SDKMessage`를 push한 배열을 `JSON.stringify`로 저장하며, 마지막 원소가
   `type: "result"` 메시지(`subtype`·`is_error`·`num_turns`·최종 `result` 텍스트 보유)다.
   실패 경로에서도 파일은 쓰인다.
4. **단, 방향 2 단독으로는 MSG-403 불변 조건을 못 지킨다** — `docs/spec/MSG-403.md` 작업 로그
   실측: 원 사고(요약 미게시 종료)에서 **`is_error: false`, `num_turns: 17`로 SDK는 정상 종료**로
   기록했다. `is_error`·`num_turns`·최종 result만 보면 그 사고를 통과시킨다. 따라서 execution
   file에서 **"요약 게시 행위"의 증거**(전사 내 게시 도구 호출)까지 함께 판정해야 한다.
   게시 도구 2종도 실측 확인: `Bash`의 `gh pr comment ...` 호출(1f115f0 방식)과
   `mcp__github_comment__update_claude_comment`(track_progress 진행 코멘트 갱신 —
   `src/mcp/github-comment-server.ts` 존재 확인, af67beb 방식).
5. 참고: 액션 자체가 `is_error: true`·result 메시지 부재 시 스텝을 실패시키는 것도 소스에서
   확인 — 검증 스텝의 result 판정은 방어선 중복이지만, 액션 버전 업데이트에 대한 보험 +
   실패 사유 로그 명확화 목적으로 유지한다.

## 판정 설계 (채택안)

검증 스텝의 판정을 "PR 코멘트 마커 grep" → "**execution file 3단 판정**"으로 교체한다.
각 단계는 실패 시 **무엇이 없어서 실패했는지 구분되는 `::error::` 메시지**를 남긴다.

| 단계 | 판정 | 실패 메시지(로그) | 잡는 사고 |
|---|---|---|---|
| ① 파일 존재 | `execution_file` output이 비어 있지 않고 해당 파일이 존재 | "execution output 파일 없음 — 액션이 산출물을 남기지 못함" | 액션 비정상 종료·출력 누락 |
| ② 실행 완주 | 마지막 result 메시지가 `is_error == false && subtype == "success"` | "실행 비정상 종료 — is_error/subtype/num_turns 실측값 출력" | 크래시·max-turns류 |
| ③ 요약 게시 증거 | 전사에 게시 도구 호출 존재: `Bash` tool_use 중 `gh pr comment`로 시작하는 command **또는** `mcp__github_comment__update_claude_comment` tool_use | "요약 게시 도구 호출 없음 — 리뷰가 결과를 PR에 남기지 않고 종료 (검사 도구: gh pr comment, update_claude_comment)" | **MSG-403 원 사고** (정상 종료·요약 미게시 — 원 사고에서 두 호출 모두 0건이었음: 체크리스트 미갱신·요약 미게시) |

- **SHA 단위 판정 유지의 논거**: execution file은 이 실행(=head SHA 체크아웃) 전용 산출물이고,
  `concurrency.cancel-in-progress`가 낡은 push의 실행을 취소하므로 마커 없이도 "현재 커밋에
  대한 판정"이 구조적으로 보장된다. (기존 마커의 SHA는 이 보장을 코멘트 텍스트로 재현하던
  수단이었다)
- **마커는 hard-fail에서 제외, warning으로 강등**: execution file 전문에 현재 SHA 마커가
  없으면 `::warning::`만 남긴다(실패 아님). 사람이 이전 push 요약과 구분하는 가독성 용도로
  프롬프트의 마커 지시는 존치하되, 지시 문구 중 "아래 검증 스텝이 이 마커로 리뷰 완주를
  판정한다"는 이제 거짓이 되므로 그 한 줄만 새 판정 방식에 맞게 보정한다(요약을 어느
  코멘트에 쓰든 본문에 마커 포함). 프롬프트 전면 개편 아님 — 마커 관련 1줄 보정만.
- 폴백(방향 1 — 탐색 범위 확대)은 **불채택**: af67beb 실측에서 요약은 issue comment(진행
  코멘트)에 있었고 마커 부재가 실패 원인이었다. 탐색 범위 확대는 관찰된 오탐을 못 고치고,
  "요약을 아예 안 남긴 경우"도 여전히 못 가린다. 방향 2가 실증됐으므로 폴백 불필요.

## 수용 기준

판정 로직은 워크플로 인라인 bash+jq다. 로컬 vitest 대상이 아니므로, 판정 스크립트를 수공
픽스처(execution file 모사 JSON)에 로컬 실행하는 것으로 로직을 검증하고, 실제 CI 동작은
PR 실행 관찰로 검증한다.

| # | 기준 | 유형 | 검증 방법 |
|---|------|------|----------|
| 1 | 액션 스텝에 `id`가 부여되고, 검증 스텝이 `steps.<id>.outputs.execution_file` 경로의 파일을 읽는다. output이 비었거나 파일이 없으면 실패하며 로그에 "execution output 파일 없음" 취지의 `::error::`가 남는다 | 로직 | 코드 확인 + 픽스처(파일 부재) 로컬 실행 |
| 2 | 정상 완주 픽스처(마지막 result: `is_error=false`·`subtype=success` + `gh pr comment` 게시 tool_use 포함)에서 판정이 통과한다 | 로직 | 픽스처 로컬 실행 (bash+jq) |
| 3 | af67beb형 픽스처(정상 result + `update_claude_comment` tool_use만 있고 마커 문자열 전무)에서 판정이 **통과**하고, 마커 부재 warning만 남는다 — 오탐 해소의 핵심 기준 | 로직 | 픽스처 로컬 실행 |
| 4 | MSG-403형 픽스처(정상 result이지만 게시 도구 호출 0건)에서 판정이 실패하고 "요약 게시 도구 호출 없음" 취지의 `::error::`가 남는다 | 로직 | 픽스처 로컬 실행 |
| 5 | 비정상 종료 픽스처(`is_error=true` 또는 `subtype!="success"`)에서 판정이 실패하고 `is_error`·`subtype`·`num_turns` 실측값이 로그에 출력된다 | 로직 | 픽스처 로컬 실행 |
| 6 | 판정 어디에도 PR 코멘트 API 조회(`gh pr view`)와 마커 grep이 hard-fail 조건으로 남지 않는다 | 로직 | 워크플로 diff 확인 |
| 7 | self-mod 가드 유지: 이 티켓의 PR 자체에서는 액션이 스킵되고 검증 스텝도 스킵되어 잡이 녹색으로 끝난다 | CI 관찰 | PR 실행 확인 |
| 8 | 워크플로 문법 유효: `actionlint`(미설치 시 `act`/yaml 파서 대체) 통과 + 워크플로 외 파일 무변경(`git diff --stat`이 claude-review.yml·CLAUDE.md·docs 이력만) | 게이트 | 명령 |
| 9 | 머지 후 첫 앱 PR에서: 리뷰가 정상 완주하면 검증 스텝이 통과한다 (실관찰 — 봇이 어느 코멘트에 요약을 쓰든) | CI 관찰 | 사후 관찰 (아래 검증 계획) |

**검증 프로파일**: **로직** — UI·앱 코드 변경이 전무한 CI 설정 티켓. 브라우저·Figma·a11y
절차는 해당 없음(dev 서버 무관). 자동 게이트는 vitest 대신 "픽스처 로컬 실행 + actionlint"로
대체하고, 실동작 확인은 CI 실행 관찰로 대신한다.

## 검증 계획 (CI 변경 특수성)

로컬 게이트로 실동작을 증명할 수 없는 티켓이다. 2단계로 나눈다:

1. **PR 이전 (로컬)**: 픽스처 4종에 판정 스크립트 실행(AC 2~5) + actionlint/문법 확인(AC 8).
   판정 bash를 워크플로에 넣기 전에 독립 실행 가능한 형태로 먼저 검증한다
2. **PR 자체**: self-mod 가드에 의해 **액션·검증 스텝 모두 스킵**된다(AC 7) — 즉 새 판정
   로직은 이 PR에서 실행되지 않는다. 잡이 녹색으로 끝나는 것까지만 관찰 가능
3. **머지 후**: develop 머지 후 첫 앱 PR의 claude-review 실행이 실질 검증이다(AC 9).
   특히 봇이 진행 코멘트에 요약을 이어 붙인 실행(af67beb형)이 통과하는지, 실패 시 로그
   메시지가 사유를 특정하는지 관찰하고 결과를 지라 코멘트로 환류한다

## 승인 결과 (2026-08-24 사용자 게이트)

- **3단 판정 채택** — 잔여 오탐 창(체크리스트만 갱신 후 침묵 종료)은 warning으로 관찰, 재발 실측 시 후속 조임 수용
- **마커 지시 존치 + 1줄 보정** — 완전 제거 불채택
- **머지 후 첫 앱 PR 관찰 수용** — 사전 리허설 불채택
- **브랜치 정정**: 신규 생성하지 않는다 — 워크트리 기동 브랜치 `fix/claude-review-summary-marker-false-fail`이 이 작업용 기존 브랜치이므로 그대로 사용 (기존 브랜치 정본 규칙)
