# MSG-447: [모바일] OS 권한 요청 흐름 — 위치·알림 런타임 권한

## 기획 요약

법적 약관 동의(MSG-422)와 OS 런타임 권한은 별개 축인데, 지금 코드에는 **권한 요청 시점과 거부 후 복구 동선이 없다.** 권한 자체는 이미 두 곳에서 요청되고 있다 — `shared/geolocation.ts`의 `resolveMapCenter()`가 `requestForegroundPermissionsAsync()`를, MSG-429의 `enablePush()`가 알림 권한을 부른다. **빠진 것은 "요청"이 아니라 "거부됐을 때 사용자가 되돌아올 길"이다.**

이 티켓이 채우는 구멍은 정확히 셋이다:

1. **위치 거부 후 복구 경로 없음** — `resolveMapCenter()`는 총함수라 거부를 서면 좌표로 흡수한다. 호출부는 "거부"와 "측위 실패"를 구분할 수 없어 내 위치 버튼이 조용히 서면으로 튄다. 안내도 설정 진입점도 없다.
2. **알림 권한 요청 시점이 프로필 토글뿐** — MSG-429 승인 D2가 "등록 진입점은 프로필 토글뿐"으로 못박아, 업로드하고 블러 완료를 기다리는 사용자는 **프로필 설정에 들어가 본 적이 없으면 푸시를 영영 못 받는다.** 완료 오버레이는 "알림으로 알려드릴게요"라고 약속하는데 그 약속이 지켜질 확률이 0인 경로가 있다.
3. **설정에서 권한을 바꿔도 화면이 낡은 채로 남음** — `usePushRegistration`은 마운트 시 1회만 권한을 판독한다. 우리가 "설정으로 가세요"라고 안내하고 사용자가 실제로 다녀오면, 돌아온 그 화면이 여전히 OFF를 보여준다. 안내 동선을 만들면서 이걸 안 고치면 동선이 자기 발등을 찍는다.

**핵심 판단**: 권한을 앱 첫 진입에 몰아 묻지 않는다. 위치는 지도가 좌표를 필요로 할 때, 알림은 완료 통지를 약속하는 그 순간에 묻는다.

## 현황 실측 (재사용 대상 확정)

|------|------|------------------|

## 수용 기준

### A. 위치 권한 (지도 홈)

| # | 기준 | 유형 | 검증 방법 |
|---|------|------|----------|
| 1 | 지도 홈 첫 진입에서 위치 권한을 요청한다(현행 유지). 허용하면 카메라가 현재 위치로 이동하고, 거부하면 서면 중심에 그대로 머문다 — 거부 시 **초기 진입에는 안내를 띄우지 않는다**(방금 사용자가 내린 결정을 되묻지 않는다) | 화면+로직 | vitest + 실기 |
| 2 | 내 위치 버튼을 눌렀을 때 권한이 없으면 **카메라를 움직이지 않고** 안내 모달을 띄운다. 현행처럼 서면으로 튀지 않는다 — 사용자가 보던 위치를 권한 거부의 부작용으로 잃지 않는다 | 화면+로직 | vitest(파생) + 실기 |
| 3 | 안내 모달의 복구 CTA가 권한 상태에 따라 갈린다: 다시 물을 수 있으면(`undetermined`) [권한 요청]이 OS 프롬프트를 다시 띄우고, "다시 묻지 않음"으로 영구 거부(`denied`)면 [설정 열기]가 시스템 앱 설정을 연다 | 로직 | vitest (순수 파생) |
| 4 | 권한이 있는데 측위만 실패한 경우(실내·에뮬레이터 타임아웃)는 **권한 안내를 띄우지 않고** 현행대로 서면 폴백 좌표로 이동한다 — 권한 문제가 아닌 것을 권한 문제로 안내하지 않는다 | 로직 | vitest |
| 5 | 설정에서 위치 권한을 켜고 돌아와 내 위치를 다시 누르면 안내 없이 현재 위치로 이동한다 (매 탭마다 상태를 새로 읽는다) | 화면 | 실기 |
| 6 | 기존 호출부 3곳(`use-region-stat-query`·`use-upload-location`·지도 초기 중심)의 동작이 바뀌지 않는다 — `resolveMapCenter()`의 총함수 계약(절대 reject 않음)과 서면 폴백이 그대로다 | 로직 | vitest (기존 `geolocation.test.ts` 무회귀) |

### B. 알림 권한 (업로드 완료 맥락)

| # | 기준 | 유형 | 검증 방법 |
|---|------|------|----------|
| 7 | 업로드 완료 오버레이("알림으로 알려드릴게요")가 뜨는 시점에, 알림 권한을 **아직 물어본 적이 없을 때만**(`undetermined`) OS 권한을 요청하고 허용 시 FCM 토큰까지 등록한다. 앱 첫 진입·로그인·지도 진입에서는 알림 권한을 묻지 않는다 | 로직+화면 | vitest(순수 판정) + 실기 |
| 8 | 이미 거부(`denied`)된 상태면 **프롬프트를 다시 띄우지 않고**, 완료 오버레이 안에 "알림 권한이 없어 완료 알림을 받을 수 없다"는 안내와 [설정 열기]를 보여준다. 업로드 자체는 정상 완료로 남고 [확인]은 그대로 동작한다 | 화면+로직 | vitest + 실기 |
| 9 | 이미 허용(`granted`)된 상태면 프롬프트도 안내도 뜨지 않는다. **프로필 토글로 푸시를 꺼둔 사용자(권한 허용 + 보관 토큰 없음)에게 몰래 재등록하지 않는다** — 사용자가 내린 OFF 결정을 업로드가 뒤집지 않는다 | 로직 | vitest |
| 10 | 알림 권한 요청 결과와 무관하게 업로드 완료 화면의 기존 요소(체크 아이콘·제목·설명·블러 안내 토스트·[확인])와 [확인]의 동작(업로드 스택 해제 + 홈 복귀 + 플로우 초기화)이 그대로다 | 화면 | 실기 + 기존 테스트 무회귀 |

### C. 서버 설정 × OS 권한 조합 (프로필)

| # | 기준 | 유형 | 검증 방법 |
|---|------|------|----------|
| 11 | **"서버 ON + OS 거부"** 조합에서 `알림 받기` 토글은 **OFF**로 보이고(MSG-429 표시 정본 유지), 행 아래에 `기기 설정에서 알림 권한을 허용해야 푸시를 받을 수 있어요` + **[설정 열기]** 가 함께 보인다. 지금은 같은 문구가 탭할 수 없는 텍스트로만 있어 사용자가 갈 곳이 없다 | 화면+로직 | vitest(순수 파생) + 실기 |
| 12 | 실패 사유 우선순위가 유지된다 — 권한 거부가 저장 실패보다 우선한다("잠시 후 다시 시도"는 설정을 열기 전까지 영원히 거짓이다). 저장 실패 단독이면 기존 텍스트 안내가 그대로 나온다 | 로직 | vitest (`notification-toggle.test.ts` 확장) |
| 13 | 설정 앱에서 알림 권한을 켜고 프로필 화면으로 **복귀하면**(화면 재마운트 없이) 토글 표시가 현재 권한 상태로 갱신된다. 지금은 마운트 시 1회 판독뿐이라 우리가 안내한 설정 왕복이 끝나도 화면이 낡은 채로 남는다 | 로직+화면 | vitest(재판독 트리거) + 실기 |
| 14 | "다시 묻지 않음" 영구 거부에서도 토글 조작·프로필 화면 어느 것도 잠기지 않는다 — 토글 탭은 서버 preferences 저장을 계속 수행하고(별개 축), 푸시 축만 거부로 남으며 설정 안내가 보인다 | 화면+로직 | vitest + 실기 |

**검증 프로파일**: **화면** — 안내 모달·완료 오버레이 안내·프로필 설정 링크가 시각 산출물이고, 권한 프롬프트 실동작은 실기로만 확인된다. Figma 정본 노드는 **없다**(권한 안내는 시안에 없는 신규 동선) → 문구·레이아웃은 기존 컴포넌트(ModalCard·Toast)와 토큰 규칙으로 판정하고 Figma 대조는 해당 없음 처리한다.

## 결정 (D)

**D1. 위치 권한 상태를 `resolveMapCenter()`의 형제 함수로 노출한다 — 기존 함수는 존치.**
`resolveMapCenter()`를 `{center, permission}` 반환으로 바꾸면 3개 호출부를 전부 고쳐야 하고, 그중 둘(도감 지역 통계·업로드 위치)은 권한을 알 필요가 없다. `resolveMapCenterWithPermission()`을 신설하고 `resolveMapCenter()`를 그 `.center` 파생으로 남긴다. 지도 홈만 새 함수를 쓴다.
*기각안*: 호출부 전면 교체 — 무관한 파일 2개가 diff에 들어오고 MSG-317이 고정한 총함수 계약 테스트를 재작성해야 한다.

**D2. 3상태 권한 타입을 `shared/permission-state.ts`로 승격한다.**
MSG-429가 이미 `granted`/`denied`/`undetermined` 3상태와 `{granted, canAskAgain}` → 3상태 매핑을 갖고 있다. 위치 축이 **똑같은** 매핑을 필요로 하므로 두 벌을 만들지 않는다. `shared/`인 이유는 `shared/geolocation.ts`가 이 타입을 쓰는데 shared는 features를 import할 수 없기 때문이다(FSD). `PushPermissionStatus`는 별칭 1줄로 남겨 MSG-429 코드·주석·테스트를 건드리지 않는다.
*판정 근거*: `denied` = `canAskAgain === false` = 안드로이드 "다시 묻지 않음". 두 축이 이 의미까지 동일하다.

**D3. 업로드 완료 시점 알림 요청은 `undetermined`일 때만 — MSG-429 D2의 의도적 확장.**
MSG-429 승인 D2는 "등록 진입점은 프로필 토글뿐 — 거부되면 되살릴 진입점이 사라진다"였다. 이 티켓이 설정 복구 동선을 만들면서 그 전제가 바뀐다(되살릴 진입점이 생겼다). 다만 확장을 **최소로** 묶는다: `granted`인데 토큰이 없는 상태는 **사용자가 토글로 끈 것**이므로 재등록하지 않는다. 즉 자동 등록은 "한 번도 안 물어본 사용자"에게만 일어난다.
*기각안*: 완료 시점에 무조건 `enablePush()` 호출 — 토글로 꺼둔 사용자의 결정을 업로드가 조용히 뒤집는다.
*기각안*: 앱 첫 진입에 알림 권한 요청 — 티켓이 명시적으로 금지.

**D4. `setting-rows.tsx`를 건드리지 않고 설정 링크를 붙인다 (MSG-448 소유권 존중).**
`SettingToggleRow`의 `errorText`는 탭할 수 없는 `Text`다. 여기에 CTA를 넣으려면 그 파일을 고쳐야 한다. 대신 **권한 거부일 때는 `errorText`를 넘기지 않고** 프로필 화면이 토글 행 **바로 아래**에 `PermissionSettingsNotice`(문구 + [설정 열기])를 렌더한다. 저장 실패 단독은 기존 `errorText` 경로 그대로다. 판정은 순수 함수(`resolveNotificationNotice`)가 소유한다.
*결과*: `features/profile/ui/setting-rows.tsx` 변경 **0줄**. 충돌 위험 없음.

**D5. 안내 UI는 위치=모달, 알림=인라인.**
위치는 사용자가 방금 버튼을 눌러 기대한 동작이 안 일어난 것이라 **차단형 모달**(ModalCard)이 맞다 — 놓치면 왜 안 움직이는지 알 길이 없다. 알림은 사용자가 요청하지 않은 부가 정보라 화면을 막지 않는 **인라인 안내**로 둔다(업로드 완료 오버레이 안, 프로필 토글 행 아래). 둘 다 기존 ui-native 컴포넌트 조립이며 신규 컴포넌트·배럴 export가 없다.

**D6. 포그라운드 복귀 재판독은 `usePushRegistration` 내부에 넣는다.**
프로필 화면이 AppState를 직접 구독하면 화면이 권한 판독 책임을 갖게 된다. 이미 마운트 시 판독을 소유한 훅에 트리거만 하나 더 다는 것이 최소 변경이다. 위치 축은 매 탭마다 새로 읽으므로 재판독 장치가 필요 없다(기준 5).

## 추정 (사용자 확인 필요 시 표기)

- **추정 1**: 위치 안내 모달 문구 — `위치 권한이 필요해요` / `현재 위치를 지도에 표시하려면 기기 설정에서 위치 권한을 허용해주세요` (Figma 시안 없음, 기존 문구 톤 승계)
- **추정 2**: 업로드 완료 거부 안내 문구 — 기존 `PUSH_PERMISSION_DENIED_MESSAGE`("기기 설정에서 알림 권한을 허용해야 푸시를 받을 수 있어요")를 **재사용**한다. 완료 화면 전용 문구를 새로 만들지 않는다
- **추정 3**: 설정 CTA 라벨 = `설정 열기` (안드로이드 관례)
- **추정 4**: `Linking.openSettings()`가 실패해도(제조사 스킨 등) 크래시하지 않도록 삼킨다 — 안내 모달은 닫힌다

## 리스크

- **R1**: OS 권한 프롬프트는 vitest로 재현 불가 — 순수 판정(상태→CTA, 상태→요청 여부)만 단위 테스트하고 실제 프롬프트·설정 앱 이동은 **실기 검증**으로만 확인한다 (page-verification 3-B)

## 검증이 잡은 결함 2건

두 건 모두 **정적 게이트 6종을 전부 통과한 상태에서 실기가 잡았다.** MSG-449가 검증 경로를 대상 앱으로 분기한 판단이 이 티켓에서 값을 했다.

1. **설정 왕복 복귀 반영 실패 (기준 13)** — 권한 거부 안내를 띄우고 사용자를 시스템 설정으로 내보냈는데, 권한을 켜고 돌아온 화면이 **여전히 "권한을 허용해야 한다"고 말했다.** 포그라운드 재판독이 `permission`만 갱신하고 조작 오류 `error="denied"`를 남겨 둔 탓. 이 티켓이 만든 복구 동선이 자기 발등을 찍는 형태라 치명적이었다.
   - 수정: `reconcilePushError(current, devicePermission)` 순수 함수 + 재판독 지점 호출.
   - **안내 파생 쪽을 고치지 않은 이유**: 토글을 막 거부한 직후에는 재판독이 도착하지 않아 `pushError`가 유일한 근거다. 파생이 그 값을 무시하면 즉시 피드백이 사라진다. 낡음을 판정할 수 있는 곳은 **새 사실이 도착하는 지점**뿐이다.
2. **안내 본문 ↔ CTA 불일치** — 재요청 가능한 상태의 모달이 **[권한 요청]** 버튼 위에 "**기기 설정에서** 허용해주세요"를 띄웠다. 시키는 대로 설정에 다녀와도 그 상태에서는 바꿀 항목 자체가 없어 헛걸음한다.
   - 수정: `AXIS_COPY`를 `{title, request, settings}`로 분리해 복구 수단마다 본문을 갖게 하고, 축×상태 전 조합을 테스트가 전수 검증.
