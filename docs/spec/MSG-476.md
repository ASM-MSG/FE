# MSG-476: 업로드 미리보기 공개 범위 선택 + 블러 처리 안내 제거

## 기획 요약

QA 2건. ① 업로드 3/3 미리보기에 공개 범위 선택(전체 공개 기본 / 나만 보기)을 추가하고 확정 `POST /api/videos` body에 `visibility`를 싣는다 — 서버 계약(`VideoUploadRequestDto.visibility`)은 현 생성 스냅샷에 이미 있어 재생성 불필요. ② 서버가 블러 처리를 껐으므로(BE MSG-456) "게시 후 얼굴과 번호판을 자동으로 가려요…"류 안내와 블러 완료 폴링·토스트·확인 모달 경로를 호출되지 않게 끊는다. 삭제 범위(완전 제거 vs 진입 차단)는 이 스펙의 결정 사항이다. 모바일 업로드는 범위 밖.

## 코드 실측 (스펙 근거)

- **`VideoUploadRequestDto.visibility`** (`shared/api/generated/types.gen.ts:302`): TS 타입은 `visibility?: string` (옵셔널·비리터럴), 주석 정본 **"공개범위. PUBLIC, PRIVATE, FRIENDS 중 하나. 생략 시 PUBLIC"**. 구체 enum은 재생 응답 쪽 리터럴로 실측됨: `visibility: 'PUBLIC' | 'PRIVATE' | 'FRIENDS'` (types.gen.ts:3126). → **전송값은 `"PUBLIC" | "PRIVATE"` 2종만 사용** (FRIENDS는 친구 기능 부재로 웹 미노출 — MSG-411 기존 결정 준용).
- **교체 DTO에는 visibility 없음**: `VideoReplaceRequestDto`는 s3Key·lat?·lng?·durationSec(·recordedAt)뿐 — 교체 모드는 공개 범위를 보낼 수 없다.
- **공개 범위 옵션 선례**: `features/video-actions/model/video-menu.ts`의 `VISIBILITY_OPTIONS`(`PUBLIC`="전체 공개", `PRIVATE`="나만 보기") + `VideoVisibility` 유니온 — 순수 모듈, 재사용 가능.
- **visibility 미전송 현황**: `use-upload-mutations.ts` `useConfirmUpload` finalize body는 s3Key·lat·lng·durationSec·recordedAt만 (245행 부근, 테스트 `use-upload-mutations.test.tsx:243`이 `not.toHaveProperty("visibility")`를 단정 — 이 단정을 뒤집는다). 티켓이 지목한 `upload-orchestration.ts`는 순수 단계열 상태 머신이라 body를 모른다 — **실제 body 조립 지점은 `use-upload-mutations.ts`** (기획-코드 지목 어긋남, 리스크 1).
- **블러 파이프라인 진입점 실측** (전체 사슬):
  1. `useConfirmUpload.onSuccess` / `useReplaceVideo.onSuccess`의 `track(videoId, now)` → `processing-store` → `pendingVideoStorage`(localStorage) 등록
  2. `AppLayout.tsx:32`의 `<UploadProcessingNotices />` 상주 → `use-processing-watcher`가 pending 구독 + hydrate로 30초 폴링(`processing-poll`) 시작 → READY/FAILED/만료 → `BlurNoticeToast` → `BlurConfirmModal`
  3. 문구: `SelectStep.tsx:133-136` 다크 InfoBox("업로드 후 AI 자동 블러 / 게시 후 얼굴과 번호판을 자동으로 가려요. 처리가 끝나면 알려드릴게요"), `wizard-mode.ts:20` 완료 안내("잠시 후 AI가 영상 블러 처리를 마치면 알림으로 알려드릴게요")
- **라디오 그룹 재료**: ui-web `Selector type="radio"`는 Radix **Checkbox** 기반(role=checkbox)이라 radiogroup 의미를 못 만든다. `radix-ui` 패키지(apps/web 의존성에 이미 있음)의 `RadioGroup` 프리미티브가 미사용 상태로 존재 — 이걸 쓴다.
- **브랜치**: 이 워크트리의 현재 브랜치가 이미 `feat/upload-visibility-and-blur-removal`이고 `origin/develop` 최신(4639232)에서 갈라져 있다(사용자 생성 브랜치 = 정본, 신규 생성 불필요).

## 결정 사항: 블러 경로 — 완전 삭제 vs 진입 차단

서버가 블러를 **"당분간"** 끈 것(MSG-456)이므로 복원 가능성이 판단 축이다.

| 관점 | A. 완전 삭제 | B. 진입 차단 (권고) |
|---|---|---|
| 대상 | `processing-poll`·`processing-store`·`use-processing-watcher`·`UploadProcessingNotices`·`BlurNoticeToast`·`BlurConfirmModal` + 테스트 3파일 + `shared/storage`의 `pendingVideoStorage`(소비자가 upload뿐) 삭제 | `track()` 호출 2곳 제거 + `AppLayout`의 `<UploadProcessingNotices />` 언마운트 + 문구 2곳 교체. 모듈·테스트는 존치 |
| diff 크기 | 약 7모듈 + 테스트 700줄± 삭제, `shared/storage.ts`까지 침범 | 실질 4~5파일 소폭 수정 — QA 웨이브 병렬(리스크 2)과 충돌 최소 |
| 복원 비용 | git revert — 그러나 주변 파일이 계속 진화해 충돌 가능성 높음, "당분간"의 기간 미상 | 진입점 2곳 되살리기(수 줄). 폴링·토스트·모달 로직과 그 테스트가 그대로 살아 있어 회귀 없이 재점등 |
| 죽은 코드 부담 | 없음 | 미호출 모듈 6개 잔존 — 단 각자 단위 테스트가 계속 돌아 부패를 감지하고, 미렌더 존치 선례 있음(`CellDetailSheet` — STATUS.md 존치 결정) |
| 티켓 문구 정합 | "호출되지 않게 끊는다" 충족 | 동일 충족 — 티켓이 삭제 범위를 스펙 결정으로 명시 위임 |

**사용자 승인 결정 (2026-08-25): A. 완전 삭제.** 하네스 권고는 B였으나 사용자가 A를 선택했다 — 이 스펙의 정본은 A다.

**재현 실측 (2026-08-26, 1080p 8.1MB 소스)**: 확정 후 **88초간 요청 0건·화면 무변화** → 새로고침하니 격자 카운트 **7 → 8**로 갱신.

## 처방 — 슬림 READY 워처 (사용자 승인, 진입 차단·후속 티켓 대안 기각)

`features/upload/model/ready-poll.ts` 신설 + `api/start-ready-refresh.ts`로 배선. **재무효화 책임만** 되살리고 통지 UI는 부활하지 않는다.

| 항목 | 값 |
|---|---|
| 첫 조회 | 확정 5초 뒤 (구 30초 대비 반영을 앞당김) |
| 이후 간격 | 30초 (구 블러 폴링과 동일 부하) |
| 상한 | 15분 — 넘기면 포기하고 자연 재조회에 맡긴다 |
| READY | `invalidateUploadSurfaces` 1회 후 중단 (확정 시점과 **같은 집합**) |
| FAILED·만료 | **조용히 중단** (토스트·확인 모달·재업로드 유도 없음) |
| 조회 실패 | 전이 아님 — 다음 간격에 재조회 |
| 중복 방어 | 영상당 폴링 1개(모듈 수준 Set), 종료 시 자동 해제 |

배선 지점은 `useConfirmUpload`·`useReplaceVideo`의 `onSuccess` 각 1줄. 교체본도 새 인코딩을 거치므로 동일 적용.

## 수용 기준 7 수정

- 종전: "확정 성공 시 `track()` 미호출 — 폴링 GET 미발사"
- **개정: "블러 통지 폴링·토스트·확인 모달이 없다. READY 반영용 폴링은 있으며, READY 전이에서 격자 쿼리를 재무효화하고 스스로 멈춘다."**

`localStorage`(`fillmap.upload.pending:v1`) 대기 목록은 여전히 쓰지 않는다 — 폴링은 세션 메모리에만 산다.

## 검토한 대안 (기각)

- **지연 재무효화(5·15·40초 setTimeout)** — 폴링 0, 코드 ~15줄. 서버 인코딩이 40초를 넘기면 여전히 놓치는데, 재현 실측이 60초를 넘겼다.
- **후속 티켓으로 분리** — 업로드 핵심 흐름의 회귀를 이 티켓이 만들었으므로 여기서 닫는 것이 맞다.

## 남은 함정 (검증 환경)

`document.hidden` 상태에서는 Chrome이 미디어 디코딩과 ffmpeg.wasm 워커를 미룬다 — 터미널이 브라우저 창을 가리기만 해도 occluded로 잡혀 `duration`이 null로 남고 트리밍이 멈춘다. 자동화로 업로드 플로우를 검증할 때는 **Chrome 창이 실제로 보이는 상태**여야 한다.


## 후속 보수 — 무효화 범위 어긋남 (같은 날 2차 QA)

첫 처방 뒤에도 "처리 중에서 안 바뀐다"가 남았다. 원인은 폴링이 아니라 **무효화 범위**였다.

- READY 폴링은 `invalidateGridQueries`만 불렀다 → 홈 격자 상세(`getGridVideos`·`getGridGlobalVideos`)는 갱신되지만
- **도감 갤러리는 `getRegionVideos`를 쓰는데 그 집합 밖**이라 READY가 돼도 영영 "처리 중"에 머물렀다
- 확정(`useConfirmUpload`)도 region-videos를 무효화하지 않고 있었다 — 교체(`useReplaceVideo`)만 하고 있었다

**처방**: `api/invalidate-upload-surfaces.ts` 신설로 무효화 집합을 하나로 모으고, **확정·교체·READY 세 지점이 모두 이 함수를 부른다.**

| 집합 | 대상 |
|---|---|
| ① 단건 재생 | `getPlayback` — 썸네일·playbackUrl·처리 상태 |
| ② 격자 | `invalidateGridQueries`(격자 영상 2종·셀·통계·점령·집계) |
| ③ 도감 | `getRegionVideos` 부분 키(regionCode 전 파라미터) |
| ④ 잔디 | `getUploadHistory` |

**원칙**: READY 재무효화의 목적이 "확정 시점 재조회가 헛발이었으니 데이터가 생긴 뒤 다시 한다"이므로, 두 시점은 **정의상 같은 집합**이어야 한다. 갈라지면 한쪽에만 있는 화면이 영구히 스테일이 된다 — 이번 도감 사례가 정확히 그것이다.

부수 효과: 확정/교체 `onSuccess` 중복이 사라져 두 훅이 각각 4줄로 줄었다.


## 세션 경계 (codex 리뷰 2회 반영)

폴링이 컴포넌트가 아니라 모듈 소유의 분리된 타이머라 화면 언마운트를 넘어 산다(모달을 닫아도 계속 도는 것이 목적). 그래서 세션 경계를 직접 지켜야 한다.

| 리뷰 | 지적 | 처방 |
|---|---|---|
| 1차 P2 | 로그아웃 후에도 폴링이 남아 **다음 사용자 토큰으로** 이전 영상을 조회하고 그 캐시를 무효화한다 | auth-store 구독 → 세션 변화 시 전량 중지 |
| 2차 P2 | 확정 요청 **도중** 로그아웃하면 `onSuccess`가 전이 이후에 도착해 구독이 그 전이를 못 본다 | 판정 기준을 이벤트가 아니라 **시작 시점 액세스 토큰**으로 변경 — 토큰 없으면 시작 안 함, 토큰이 바뀌면 전량 중지 |

테스트 5건으로 고정: 로그아웃 시 중지 · 로그아웃 후 READY여도 새 세션 캐시 미무효화 · **로그아웃 뒤 도착한 확정은 폴링 미시작** · 계정 전환 시 미무효화 · 영상당 폴링 1개.
