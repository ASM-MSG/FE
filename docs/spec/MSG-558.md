# MSG-558: [모바일] 줌아웃 행정 단위 집계 마커 말풍선 리디자인 (웹 MSG-475 대응)

## 기획 요약

앱 지도 홈의 저줌(zoom < 16) 행정 단위 집계 마커는 MSG-428 시점의 **파란 원형(동 68 / 구 80, 흰 링 3px)** 그대로다. 웹은 MSG-475에서 같은 마커를 **말풍선(라운드 10 · 패딩 6/12/7 · 링 없음 · 그림자 · 2줄 지역명/개수 · 크기 단일)** 으로 바꿨다. 이 티켓은 앱 `features/map-home`의 집계 마커 **렌더만** 웹 구현과 같은 형태로 교체한다. 집계 단위 전환·탭 드릴인·겹침 병합·격자 복귀는 기존 동작 그대로다.

**플랫폼: `apps/mobile` 전용. `apps/web`·`packages/ui-web`은 읽기만 하고 한 줄도 수정하지 않는다.** 디자인 정본은 Figma가 아니라 **웹 코드**(`apps/web/src/pages/map-home/ui/MapCanvas.tsx` `clusterMarkerContent`, 사용자 지시 2026-09-02)다 — Figma 탐색은 지시에 따라 생략했다.

### 네이버 지도 RN 마커 렌더링 방식 (`@mj-studio/react-native-naver-map@2.9.0` 소스 실측)

`apps/mobile/node_modules/@mj-studio/react-native-naver-map/src/component/NaverMapMarkerOverlay.tsx` `image` prop JSDoc — 마커 종류 5가지: ① SDK 기본 심벌 ② 로컬 이미지(`require`, 캐싱 ✅) ③ 네이티브 리소스 ④ 네트워크 이미지 ⑤ **커스텀 React View(`children`, 캐싱 ❌)**. ⑤의 계약:
- `children`은 1개 이하(`nAssert`), 뷰들에 `collapsable={false}`, **`width`·`height` prop 필수**("되도록 모두 사용 — 없으면 debug/release 크기가 다르게 나옴")
- **"마커의 생김새를 바꿔야 한다면 그 의존성들을 제일 상위 자식의 `key`로 전달해야 한다"** — Android는 RN Shadow Node를 커스텀해 실제 `View`를 삽입, iOS는 `UIView`를 `UIImage`로 캔버스에 그린다
- **"이 타입은 많이 생성될 시 성능에 굉장히 영향 — 단순하게 쓰거나 되도록 이미지 권장"**, 마커당 리소스 큼
- 충돌 옵션 `isHideCollidedMarkers`·`isHideCollidedCaptions`·`isForceShowIcon`·`zIndex`, 텍스트 `caption`/`subCaption`(색·크기·정렬만, **굵기 불가**) 존재

**앱 현행 원형 마커 = ⑤ 커스텀 뷰**(`grid-map.tsx:447~459` — `NaverMapMarkerOverlay width/height={CLUSTER_MARKER_PX[unit]} anchor 0.5/0.5 onTap` + `<ClusterMarker>`). 경로 번호 마커(MSG-298)·미션 이름표(MSG-427)도 같은 방식이다.

**판단 — 권장안: ⑤ 커스텀 뷰 유지.** 말풍선(라운드 사각 + 2줄 텍스트 + 그림자)은 `View`+`Text` `style`만으로 그려지고 꼬리가 없어 SVG 불필요. 성능 제약은 MSG-428이 같은 방식·같은 마커 수로 이미 수용한 리스크(R6)이고, 마커 수는 뷰포트 × 행정 단위 × 병합으로 눌린다(동 단위 부산 전역 ≈ 200여 동이지만 뷰포트가 1° 상한 클램프 + 화면 안만 응답). 실기 검증에서 프레임 저하가 보이면 리스크 R5 대안으로 내려간다.
**대안: ② 이미지 + `caption`/`subCaption`.** 말풍선 PNG 1장(캐싱 ✅) 위에 네이티브 캡션 2줄(`align: "Center"`) — 마커당 리소스가 가장 작다. 대가: 캡션 굵기 지정 불가(개수 bold 불가), 폭 hug 불가(`width`로 늘리면 라운드 10이 왜곡 — 9-patch 미지원), 85% 알파는 `color` rgba로 가능. 정본 재현도가 떨어지므로 성능 실측에서 필요할 때만 채택.

### 앱 핫구역 집계·SIDO 확인 (티켓 [제외 범위] 조사 결과)

- **핫구역 행정 단위 집계 — 앱에 없다.** `apps/mobile/src`에서 `getHotZoneAggregates`·`hotzones/aggregation` 0건. 앱은 개별 조회 `api/use-hotzones-query.ts`(`GET /api/hotzones`, 로그인 게이트)와 `use-home-overlays.ts`의 `hotGridIds` 격자 낱개만 있다. 생성 SDK(`getHotZoneAggregates`)는 `shared/api/sdk.ts`가 웹 생성물을 재수출하므로 **호출 가능한 상태**지만 훅·마커 파생·게이트가 전부 없다. 게다가 앱은 칩 활성 중 집계 마커를 억제(MSG-428 Q4)하므로 핫 칩 저줌은 격자 낱개 그대로 → 웹 MSG-475 ③ 대응은 **별도 티켓**(훅 + `toHotZoneClusterMarkers` 포팅 + `hotCellsVisible` 게이트 + 칩 택일 규칙).
- **SIDO — 앱 `aggregation-unit.ts`는 웹과 같은 3단(`DONG|SIGUNGU|SIDO`) 테이블**이고, `MAP_MIN_ZOOM = 10`으로 SIDO 구간(zoom 6~9) 도달만 막는다(MSG-428 승인 Q2). 이 티켓이 크기 3단을 폐기하면 마커 렌더에 unit 분기 자체가 사라지므로 SIDO 말풍선은 **코드상 자동 지원**(별도 작업 없음), 도달 불가는 그대로다. 티켓 조건 "웹과 같으면 포함"에 해당 → 포함(추가 구현 0).
