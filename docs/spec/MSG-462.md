# MSG-462: 지도 줌 속도 완화 + 축제·팝업 영역 격자를 누르면 그 행사 상세가 열리게

## 기획 요약

프론트 QA 지적 2건. ① 지도 확대·축소가 너무 빨라(휠·트랙패드·핀치·줌 버튼) 원하는 축척에서 멈추기 어렵다 — 속도를 완화한다. ② 지역축제·팝업스토어 칩 활성 상태에서 영역 안 격자를 누르면 격자 상세("서면 I-7")가 떠서 그 자리가 어떤 행사인지 알 수 없다 — 영역 안 어디를 누르든 그 행사의 미션 상세(기존 `MissionDetailPanel`)가 열리게 한다. 신규 연동 API는 `GET /api/grids/{gridId}/missions` 하나뿐이고, 비로그인에서도 상세가 열려야 한다(서버 MSG-454 완료).

## 현황 실측 (코드 대조 결과)

- **줌 경로**: `MapCanvas.tsx`의 `NaverMap`에 줌 속도 관련 옵션이 없다(기본값). 줌 버튼은 `zoomIn`/`zoomOut` 명령(`setZoom(±1, true)` 애니메이션), 휠·핀치는 SDK 내부 기본 동작. 네이버 SDK `MapOptions`에는 줌 "속도" 옵션 자체가 없다(`scrollWheel`·`pinchZoom`은 불리언 on/off뿐) — 완화하려면 `scrollWheel` 비활성 + 자체 휠 리스너로 스텝을 제어하는 길뿐이다.
- **격자 클릭 경로**: `MapCanvas` 셀 클릭 → `MapShell.handleCellClick`(`grid-click-routing.buildCellClickHandler`: **점령 격자면 무조건 격자 상세** — MSG-329) → 비점령이면 `map-overlay-store.onCellClick` → 홈의 `use-home-overlay-publish.handleCellTap` → `canOpenDetail` 판정 후 `selectCell(cellId)` → `panel-branch`가 `selectedGridId !== null`이면 **"grid-detail"** 로 분기. 즉 칩 활성 중 미션 격자를 눌러도 격자 상세가 뜨는 것이 현행이다.
- **미션 상세 열림 경로**: `mission-selection-store.select(missionId)` → `use-home-panel-state`가 활성 칩 목록(`missionViews`)에서 그 미션을 찾을 때만 `"mission-detail"` 분기 → `MissionDetailPanel`. 상세가 열리면 `use-home-overlays`가 그 미션만 자기 경계로 그리고 이름표를 함께 게시한다(요구 6은 기존 경로 재사용으로 충족).
- **미션 API 게이트**: `use-active-missions-query`·`use-mission-detail-query`·`use-mission-videos-query`·`use-mission-progress-query` 전부 `isAuthenticated` 게이트(MSG-403, 익명 401 실측 시점 결정). 비로그인이면 칩을 켜도 미션 목록이 안 떠서 영역 자체가 안 그려진다 — 요구 8과 충돌하는 현행.
- **신규 API 계약 실측** (`shared/api/generated/sdk.gen.ts` 주석): `GET /api/grids/{gridId}/missions`는 **"격자가 대표 격자인 미션 조회"** — 판정 범위(축제 9×9)에만 걸친 격자는 **빈 배열**이고, 대표 격자(영상이 모인 칸)일 때만 미션이 나온다. 정렬은 진행 중 → 시작 전 → 종료(첫 항목이 화면 진입 기본값), 기간 필터 없음, 비로그인 조회 가능, 오류가 아니라 빈 배열. → **티켓의 "영역 안 어디를 누르든"을 API 단독으로는 만족할 수 없다** (아래 추정 1의 하이브리드 판정 근거).
- SDK `getMissionsByGrid` + `getMissionsByGridOptions`(react-query gen)는 이미 생성돼 있다. 재생성 금지.

## 추정 및 질문 (사용자 확인 필요)

1. **[핵심] 하이브리드 판정 (수용 기준 6)** — 실측 결과 신규 API는 **대표 격자에서만** 미션을 답한다(판정 범위 9×9 격자는 빈 배열). 티켓의 "영역 안 어디를 누르든"은 API 단독으로 불가능해, **API 우선 + FE 도형 소속 폴백**의 하이브리드로 계획했다. "한 격자가 여러 미션에 걸리면 응답의 첫 항목" 규칙은 API가 답한 경우에 적용되고, FE 폴백에서는 활성 목록 순서의 첫 미션이다. 이 해석 승인 필요 — 대안(FE 소속 단독 판정)은 API 연동 요구와 "응답의 첫 항목" 문구를 못 살린다.
2. **type 불일치 처리** — 응답 첫 항목의 type이 활성 칩과 다르면(축제 칩인데 첫 항목이 POPUP) 그 미션은 활성 목록에 없어 상세 뷰를 만들 수 없다. **활성 칩 type 일치 항목 중 첫 항목**으로 좁히고 칩 자동 전환은 하지 않는 것으로 추정 (티켓 문구 "응답의 첫 항목"의 보수적 해석).
3. **적용 범위 = 칩 활성 상태 한정** — 영역이 보이는 것은 축제·팝업 칩 활성 때뿐이라 QA 시나리오도 칩 활성이다. 칩이 꺼진 상태의 (점령) 격자 클릭은 종전 유지로 추정. (API 명세 주석은 "영상이 모인 칸을 눌러 무슨 미션이었는지 확인하는 경로"라 칩 밖 확장 여지가 있으나 이번 범위에서 제외 — 확장 원하면 별도 확인)
4. **익명 게이트 해제 범위** — 비로그인에서 상세가 열리려면 미션 목록(`missions/active`)·상세(`missions/{id}`)·미션 영상 게이트를 함께 풀어야 한다(목록이 없으면 영역도 상세 뷰도 없다). MSG-454가 이 범위를 다 허용했다고 추정(MSG-403의 익명 401 실측 결정 번복). "내 진행"(progress)은 사용자 데이터라 로그인 게이트 유지.
5. **줌 완화 파라미터** — 쿨다운·누적 임계 기본값은 코드 상수(단일 정의)로 두고 브라우저 검증에서 체감 튜닝한다. "느리게"의 정량 기준이 티켓에 없어 QA 재현 시나리오 완화를 판정 기준으로 삼는다.
6. **터치스크린 핀치(`pinchZoom`)는 SDK 기본 유지** — 데스크톱 웹이 정본이고 트랙패드 핀치는 ctrl+wheel로 휠 경로에 잡힌다. 터치 핀치까지 자체 구현하는 것은 비용 대비 과잉으로 추정.

## 리스크

- **API 계약 ↔ 티켓 요구 모순** (추정 1과 동일 뿌리): 대표 격자 한정 응답. 하이브리드 판정으로 흡수하지만, 서버가 이후 판정 범위 전체를 답하도록 바뀌면 FE 폴백 비중이 줄어들 뿐 동작은 동일 — 판정 함수 한 곳에 격리한다.
- **네이버 SDK에 줌 속도 옵션 부재** — `scrollWheel` off + 자체 휠 리스너가 유일 경로. `react-naver-maps@0.2.2`가 `scrollWheel` prop을 전달하는지 이 워크트리에서 미확인(node_modules 미설치) — 미전달이면 `onInit`에서 `map.setOptions`로 우회. 휠 리스너는 `passive: false` + `preventDefault` 필요.
- **MSG-329 점령 우선 라우팅과 부분 충돌** — 칩 활성 중 점령 격자가 미션 영역 안에 있으면 현행은 격자 상세가 이긴다. 칩 활성 한정 예외로 좁혀 기존 규칙 본체는 보존한다 (수용 기준 11·12가 양쪽을 고정).
