# MSG-448: [모바일] 준비 중 화면 3종 실구현 — 위치정보 동의 관리·신고 관리·약관 전문

> 대상 앱: **apps/mobile** (Expo Router + NativeWind). 웹 변경 없음.

## 기획 요약

웨이브 1~2가 화면 골격만 넣고 "준비 중"으로 남긴 사용자 노출 진입점 3종을 실제 목적지로 채운다. ① 프로필·설정 → **위치정보 동의 관리**: 현재 동의 상태 열람 + 위치기반 약관 동의 철회 + 마케팅 수신 동의 토글. ② 프로필·설정 → **신고 관리**: 내가 신고한 내역(대상·사유·시점·처리 상태) 목록 + 빈/로딩/실패 3상태. ③ 회원가입 동의의 "보기" → **약관 전문 뷰어** 1개를 4종(+프로필의 이용약관·개인정보 처리방침)이 문서 키로 공유. 약관 문구 작성과 신고 처리 로직은 범위 밖이며, 문구가 없으면 자리표시로 두고 그 사실을 보고한다.

## 실측 요약 (스펙의 전제 — 추측 아님)

코드베이스·생성 SDK를 직접 확인한 결과다. 티켓 [참고]와 어긋나는 항목이 3개 있다.

### A. 생성 SDK 엔드포인트 실재 여부

`apps/mobile/src/shared/api/sdk.ts`는 웹 생성물(`apps/web/src/shared/api/generated`)을 재수출하는 barrel이다. 전체 `url:` 목록을 grep한 결과:

| 필요 기능 | 엔드포인트 | 존재 | 비고 |
|---|---|---|---|
| 동의 상태 조회 | `GET /api/users/me/consents` (`getConsentStatus`) | **있음** | `ConsentStatusResponseDto` — `ageOver14`·`serviceTerms`·`privacyPolicy`·`locationTerms`·`marketing`·`requiredCompleted` 6필드 |
| 가입 동의 일괄 제출 | `PUT /api/users/me/consents` (`submitConsents`) | **있음** | 5항목 전부 저장. 필수 4는 true만 허용 |
| 마케팅 동의 변경 | `PUT /api/users/me/marketing-consent` (`updateMarketingConsent`) | **있음** | `{consented: boolean}` — **true·false 모두 유효**. 응답은 `ConsentStatusResponseDto` |
| 위치 동의 변경 | `PUT /api/users/me/location-consent` (`updateLocationConsent`) | 있음(제약) | **`consented:false`는 developCode 1400으로 거절 — 철회 불가** |
| **내 신고 내역 조회** | — | **없음** | `/api/admin/reports`(`getReports`)뿐 — **관리자 전용**, 쿼리는 `status`·`page`·`size`로 **신고자 필터가 없다**. 일반 사용자 토큰으로 호출 대상 아님 |
| **약관 문서 조회** | — | **없음** | `term`·`policy` 경로가 SDK에 0건 |

TanStack 옵션 배럴(`shared/api/query-options.ts`)에도 `getConsentStatusOptions`·`getConsentStatusQueryKey`·`updateMarketingConsentMutation`이 이미 재수출돼 있어 **배럴 수정 없이 사용 가능**하다.

생성물 원문 주석 2건 (서버 계약의 정본):
- `ConsentStatusResponseDto.locationTerms` — *"프로필 화면의 위치정보 사용 동의와 같은 한 값이며 **철회할 수 없다** — 한 번 true 가 되면 되돌아가지 않는다"*
- `LocationConsentUpdateRequestDto.consented` — *"true 면 동의. 이 동의는 **철회할 수 없어 false 는 1400 으로 거절된다**"*

`getMe`(`UserProfileResponseDto`)에는 `locationConsent`만 있고 **마케팅 필드가 없다** — 마케팅 현재값의 유일한 출처는 `getConsentStatus`다.

이 consents 3종은 최신 SDK 재생성(MSG-451, 2026-08-21)에 들어왔다 — `git log -S`로 확인. MSG-422(2026-08-18) 당시에는 없었다.

### B. 위치 동의 철회 시 앱 동작 (실측)

`app/_layout.tsx`의 `AppShell`은 `useConsentGate()`가 참이면 **`Stack`(네비게이터) 자체를 `SignupConsentScreen`으로 대체**한다. `useConsentGate` → `getMe`의 `locationConsent` → `shouldShowConsentGate(isAuthenticated ∧ isSuccess ∧ locationConsent === false)`.

→ **위치 동의가 false가 되는 순간 회원가입 약관 동의 게이트가 전면 복귀하고, 딥링크·`router.push`·탭 이동 어느 경로로도 우회되지 않는다.** 즉 이 앱에서 "위치 동의 철회"는 UI 상태 변화가 아니라 **앱 전체 잠금**과 동의어다. 설정 화면 자신도 게이트에 덮여 사라진다.

### C. 티켓 [참고] 스테일 3건

1. `features/grid-detail/model/report-types.ts` — **존재하지 않는다.** MSG-431이 삭제하고 `features/video-actions/model/report.ts`로 대체했다(mock 사유 5종 → 웹 정본 3종 + 서버 enum 매핑). 신고 흐름도 `features/grid-detail/ui/report-modal.tsx` + `features/video-actions/`가 소유한다.
2. `features/profile/ui/setting-rows.tsx`는 **행 프리미티브(`SettingRow`·`SettingInfoRow`·`SettingToggleRow`)만** 갖는다. "준비 중" 문자열과 행 배선은 전부 `features/profile/ui/profile-screen.tsx`에 있다 — **이 티켓은 `profile-screen.tsx`도 수정해야 한다** (질문 Q6).
3. 회원가입 "보기"는 **미배선이 아니다.** `signup-consent-screen.tsx`가 `openedTerms` 로컬 상태로 `ConsentTermsView`(게이트 내부 전면 뷰)를 이미 띄운다. 그 뷰의 본문이 "약관 전문은 준비 중이에요" 자리표시일 뿐이다.

### D. 라우팅 방식

**expo-router 파일 라우팅** (`apps/mobile/src/app/`). 기존 상세 화면 선례: `app/profile/edit.tsx`, `app/dex/history.tsx`, `app/grid/[cellId].tsx`, `app/video/[videoId].tsx`. 라우트 파일은 feature 화면 컴포넌트를 감싸는 3줄짜리 default export다. `app/profile/index.tsx`와 `app/profile/edit.tsx`가 공존하듯 `app/profile/*` 추가는 검증된 패턴이다.

**중요한 구조 제약**: 회원가입 동의 게이트는 `Stack`을 대체하므로 **게이트 안에서는 라우터 이동이 불가능**하다(MSG-422가 라우트를 만들지 않은 이유 = 잠금 누수 방지). 따라서 약관 뷰어는 "라우트"가 아니라 **프레젠테이셔널 컴포넌트**여야 하고, 라우트는 그 컴포넌트를 감싸는 얇은 층으로만 존재한다.

### E. Figma 시안 — **3종 전부 없음**

정본 페이지 `필맵 앱 디자인 MVP ver 6`(`14799:25586`, 최상위 프레임 55개) 전수 검색 결과:

## 약관 문구 부재 처리 방침

문구 작성은 기획·법무 몫이다(티켓 [제외 범위]). **임의 작성 금지.** 서버 API도 없다(실측 A — `term`·`policy` 경로 0건). 따라서 **로컬 상수 자리표시**를 쓰되, "미확정"이 세 곳에서 동시에 드러나게 한다.

1. **데이터 모델이 미확정을 1급 상태로 갖는다.** `TermsDocument.body: string | null`이고 현재 전 문서가 `null`이다. `isTermsPlaceholder(doc) = doc.body === null`. 빈 문자열 `""`이나 "준비 중입니다" 같은 **가짜 본문을 넣지 않는다** — 그러면 "문구가 있다"와 "없다"가 타입으로 구분되지 않는다.
2. **화면이 미확정을 말한다.** `body === null`이면 본문 대신 자리표시 블록을 그린다 — 제목은 정상 노출(문서 정체는 확정이다), 본문 자리에 "약관 전문은 준비 중이에요 / 문구가 확정되면 이 화면에서 바로 확인할 수 있어요"(기존 `consent-terms-view.tsx` 문구 승계). 기준 4.
3. **테스트가 미확정을 고정한다.** 기준 2가 "전 문서 `body === null`"을 단정한다 — 문구가 들어오는 순간 이 테스트가 RED가 되어 갱신을 강제한다. 조용히 반쯤 채워진 상태로 흘러가지 않는다.
4. **리포트가 미확정을 보고한다.** 검증 리포트에 "약관 5종 전부 문구 미확정 — 기획·법무 대기, 서버 API 부재"를 명시한다.
5. **서버 API가 생기면**: `TERMS_DOCUMENTS`의 `body`를 조회 결과로 갈아끼우는 것이 유일한 변경점이 되도록, 화면은 `resolveTermsDocument`의 반환만 읽는다.

프로필의 "서비스 이용약관"·"개인정보 처리방침" 행은 **`준비 중` 캡션을 떼고 활성 행으로 만든다**(기준 5). 목적지가 자리표시라도 "행이 눌리지 않는다"보다 "행이 눌리고 문서가 아직 준비 중이라고 말한다"가 정직하다 — 후자는 진행 상황을 알려주고 전자는 죽은 UI다.

## 약관 뷰어 공유 구조 (문서 키 설계)

**한 개의 프레젠테이셔널 컴포넌트를 5개 문서 × 2개 진입 경로가 공유한다.**

```
entities/terms/model/terms-documents.ts   ← 카탈로그 + 순수 조회 (도메인, 플랫폼 무의존)
entities/terms/ui/terms-document-view.tsx ← 표시 전용 (title + body|자리표시 + onClose)
      ↑                                    ↑
      │                                    │
features/auth/ui/signup-consent-screen    app/terms/[docKey].tsx
  (게이트 내부 — 라우터 사용 불가,          (라우트 — router.back())
   openedTerms 로컬 상태로 직접 렌더)
```

**`entities/terms`에 두는 이유**: 두 소비처가 `features/auth`(회원가입 게이트)와 `features/profile`(설정)로 서로 다른 feature다. 한쪽 feature에 두면 다른 feature가 그것을 import하는 **교차 feature 의존**이 생긴다. FSD에서 features 공유 자산의 자리는 `entities`다. `apps/*/shared`에 재사용 UI를 두는 것은 DESIGN_SYSTEM 명시 금지이고, `ui-native` 승격은 배럴 동결 + 도메인 인지(약관 문서) 두 이유로 불가하다.
※ 현재 `entities/*`에 `ui/`를 둔 선례가 없다(전부 `model/`뿐) — 이 티켓이 첫 사례다. FSD 규약상 적법하며, 대안(교차 feature import)이 규약 위반이라 이쪽을 택한다.

### 문서 키 카탈로그

| 키 | 제목 | 회원가입 "보기" | 프로필 행 |
|---|---|---|---|
| `service` | 서비스 이용약관 | ✔ | ✔ (서비스 이용약관) |
| `privacy-collection` | 개인정보 수집 및 이용 | ✔ | — |
| `location` | 위치기반서비스 이용약관 | ✔ | — (동의 관리 화면의 "보기") |
| `marketing` | 마케팅 정보 수신 | ✔ | — |
| `privacy-policy` | 개인정보 처리방침 | — | ✔ (개인정보 처리방침) |

- 회원가입 4종 = 티켓 [동작 요구] 그대로. 만 14세 행은 문서가 없어 "보기"도 없다(MSG-422 `termsTitle: null` 계약 승계).
- **`privacy-collection`과 `privacy-policy`를 별개 키로 둔다** — 법적으로 다른 문서이고 화면 문구도 다르다. 같은 문서라면 키 1개로 합친다 → **질문 Q2**.
- 라우트 파라미터는 이 키 문자열이다: `/terms/service`, `/terms/privacy-policy` 등.

### 기존 자산 변경

- `features/auth/model/signup-consent.ts`의 `ConsentItem.termsTitle: string | null` → **`termsDocKey: TermsDocKey | null`**로 교체하고 제목은 카탈로그에서 파생한다. MSG-422 결정("`hasTermsView: boolean` 대신 제목을 카탈로그에 둔다 — 보기 유무와 헤더 제목을 한 필드로")의 의도를 유지하면서 출처만 약관 카탈로그로 옮기는 것이다. `signup-consent.test.ts`의 해당 단정을 갱신한다.
- `features/auth/ui/consent-terms-view.tsx`는 **삭제**하고 `entities/terms/ui/terms-document-view.tsx`가 대체한다(자리표시 문구는 승계). 남기면 자리표시가 두 벌이 된다.
- `signup-consent-screen.tsx`의 `openedTerms: string | null`(제목)은 `TermsDocKey | null`로 바뀐다. 하드웨어 뒤로가기가 전문 뷰를 먼저 닫는 기존 분기(AC 22)는 그대로 유지된다.

## 위치정보 동의 관리 — 철회 설계

### 서버 계약과 티켓 요구의 충돌 (최우선 확인 사항)

티켓 [동작 요구]: *"위치기반서비스 이용약관 동의를 **철회할 수 있고**, 철회하면 서버에 반영된다"*
서버 계약(실측 A): *"이 동의는 **철회할 수 없어** false 는 1400 으로 거절된다"*

**현재 API로는 이 요구를 이행할 수 없다.** 그리고 이행할 수 있게 되더라도 실측 B가 보여주듯 철회의 실제 결과는 "설정이 꺼진다"가 아니라 **회원가입 동의 게이트가 전면 복귀해 앱 전체가 잠긴다**(설정 화면 자신도 사라진다). 웹도 같은 판단에 도달해 있다 — `DECISIONS.md` MSG-407 v3 결정 1이 **인앱 동의 접점을 제거**하고 동의를 온보딩 게이트 전용으로 못박았으며(`ProfilePanel.tsx`의 "위치정보 동의 관리" 행은 지금도 비활성), 결정 206은 *"철회 UX 후속 티켓이 오면 그 티켓의 스펙으로 다시 넣는다"*고 남겼다. **MSG-448이 그 후속 티켓이고, 지금 그 결정을 내려야 한다.**

### Q1 결정별 구현 분기

**추정 기본안 (A) — 철회 불가를 정직하게 표시 + 대체 경로 안내.** 사용자 확인 대상.

| 안 | 화면 동작 | 평가 |
|---|---|---|
| **A (추정 기본)** | 위치기반 행에 `동의함` 상태 + 철회 조작 대신 안내: "위치기반서비스 이용약관 동의는 철회할 수 없어요. 서비스 이용을 중단하려면 계정 삭제를 이용해 주세요." + `계정 삭제` 화면 진입 경로. 사전 고지 다이얼로그는 **계정 삭제 경로에 붙인다**(기존 `DeleteAccountModal` 재사용) | 서버 계약·게이트 구조·웹 선례 셋과 전부 정합. 티켓 문면과는 다름 |

| D | BE에 철회 API 신설 요청 후 이 축만 후속 티켓으로 분리, 이번엔 열람 + 마케팅 토글만 | 정직하지만 티켓의 핵심 축 하나가 비고, 게이트 전면 잠금 문제는 API가 생겨도 남는다 |

**A를 택할 경우** 기준 15·16은 이렇게 확정된다:
- 기준 16 = `canRevokeLocationConsent()`가 `false`를 돌려주고 `locationConsentNotice()`가 위 안내 문구를 파생한다(서버 계약이 판정의 단일 출처, 화면에 문구 하드코딩 금지).
- 기준 15 = 위치기반 행에 철회 조작 자체가 없고, 계정 삭제 경로에는 기존 확인 모달이 선행한다.
- 안내 문구 색은 경고가 아니라 정보이므로 `text-foreground-muted`, 계정 삭제 진입만 `red-600`.

> **위치정보 동의를 철회할까요?**
> 철회하면 지도에서 내 주변 격자를 보거나 영상을 올릴 수 없고, 앱을 계속 쓰려면 약관에 다시 동의해야 해요. 지금까지 수집한 격자와 올린 영상은 사라지지 않아요.

`ModalCard`(`confirmVariant="danger"`·`confirmDisabled`)로 띄운다 — 신규 컴포넌트 불필요.

### 마케팅 수신 동의 토글 — 서버 반영 경로 (실측)

**`use-update-location-consent.ts`는 마케팅을 다루지 않는다.** 위치 동의 전용(`PUT /api/users/me/location-consent`)이고 성공 시 `getMeQueryKey()`를 invalidate할 뿐이다. 마케팅은 **별도 엔드포인트 `PUT /api/users/me/marketing-consent`**이며 전용 mutation을 신설해야 한다.

경로: `Switch onCheckedChange` → 연타 가드(`mutationKey` in-flight) → `updateMarketingConsentMutation` → `PUT {consented}` → 응답 `ConsentStatusResponseDto`를 `getConsentStatusQueryKey()`에 **`setQueryData`로 seed**(무효화 재조회 금지 — MSG-426 알림 토글·MSG-431 공개범위 전환이 세운 정책) → 실패 시 `onError`가 이전 스냅숏 복원 + 인라인 실패 캡션.

구조는 **MSG-426의 "옵션 팩토리 + 얇은 훅" 2파일**을 그대로 따른다 — `auth-session`을 import하면 expo-secure-store가 파싱 단계에서 죽어 훅 테스트가 불가능하기 때문이고, 테스트는 `MutationObserver`로 옵션 객체를 직접 구동한다.

> 주의: 회원가입에서 마케팅을 체크해도 MSG-422는 **아무 요청도 보내지 않는다**(당시 저장 엔드포인트 부재). 따라서 가입 시 마케팅에 동의한 사용자도 이 화면에서는 OFF로 보인다 — 리스크 R7.

## 신고 내역 — 서버 미제공 대응

**내가 신고한 내역을 주는 엔드포인트가 없다**(실측 A). `/api/admin/reports`는 ① 관리자 전용이라 일반 사용자 토큰으로는 403이고 ② 쿼리에 신고자 필터가 없어 **호출이 성공한다면 그것이 곧 남의 신고까지 노출되는 사고**다. **호출하지 않는다.**

### 자리표시 전략

1. **교체 이음새를 한 파일로 고정한다.** `features/report-history/api/use-my-reports-query.ts`가 `{ items, isPending, isError, refetch }`를 돌려준다. 실 엔드포인트가 생기면 이 파일 하나만 `getMyReportsOptions()` 기반으로 갈아끼우면 되고, 화면·모델·테스트는 무변경이다.
2. **기본 반환은 빈 목록이다.** 가짜 신고 내역을 실제 사용자에게 보여주지 않는다 — 신고 내역은 "내가 무엇을 신고했는가"라는 사실 진술이고, 지어내면 화면이 거짓말을 한다.
3. **화면이 미연동을 상시 말한다**(기준 26): 목록 영역 위에 고정 안내 — "신고 내역은 서버 연동을 기다리고 있어요. 접수된 신고는 정상 처리돼요." 이것이 없으면 빈 상태가 "신고한 적 없음"으로 오독되고, 실제로 신고한 사용자에게는 거짓이 된다.
4. **3상태를 죽은 코드로 만들지 않는다.** 로딩·실패·목록 경로는 `resolveReportListState`(순수 함수)가 판정하고 기준 19~23의 vitest가 4상태 전부를 **fixture로 구동**한다. 렌더 층은 그 판정만 읽는 얇은 스위치라 미도달 분기가 아니라 미도달 **입력**만 남는다.
5. **필드 형태는 서버 DTO를 정본으로 미리 맞춘다.** `AdminReportItemResponseDto`가 이미 4필드를 전부 갖고 있다 — `videoOwnerNickname`/`videoId`(대상)·`reason`(사유)·`createdAt`(시점)·`status`(처리 상태). 로컬 타입을 이 형태의 부분집합으로 정의해 두면 실 API 도입 시 매핑이 항등에 가까워진다.
6. mock fixture는 **테스트에서만** 쓴다(`*.test.ts` 안 또는 `model/mock-report-history.ts`를 테스트만 import). 화면 기본 경로에는 들어가지 않는다 → **질문 Q3**.

### 4필드 표시 규칙

| 필드 | 출처 | 표시 |
|---|---|---|
| 대상 | `videoOwnerNickname` + `videoId` | `{닉네임}님의 영상` (닉네임 없으면 `영상 #{videoId}`) |
| 사유 | `reason` enum 5종 | 한국어 라벨. `INAPPROPRIATE` 부적절한 콘텐츠 / `PRIVACY` 사생활 침해 / `SPAM` 스팸·도배 / `COPYRIGHT` 저작권 침해 / `OTHER` 기타. 미지 값은 `기타` 폴백 (기준 21) |
| 시점 | `createdAt` (타임존 마커 없는 UTC) | KST 변환 후 `YYYY.MM.DD` — `profile-format.ts`의 `KST_OFFSET_MS` 방식 재사용 (기준 23) |
| 처리 상태 | `status` 4종 | `PENDING` 접수됨 / `REVIEWING` 검토 중 / `RESOLVED` 조치 완료 / `REJECTED` 반려됨. 미지 값은 `접수됨` 폴백 (기준 22) |

사유 라벨은 `features/video-actions/model/report.ts`의 `REPORT_REASONS`(FE 3종)와 **다른 방향의 매핑**이다 — 그쪽은 `FE id → 서버 enum`(제출), 이쪽은 `서버 enum → 라벨`(열람). 서버는 다른 클라이언트가 넣은 `COPYRIGHT`·`OTHER`도 돌려줄 수 있어 5종 전부 필요하다. 두 매핑이 같은 파일에 살면 방향이 헷갈리므로 열람용은 `features/report-history/model/`에 둔다.

### 승격 후보

**`DexErrorState`(제목 + 보조문구 + "다시 시도" 버튼)** — 자체 JSDoc이 *"사용처가 3곳을 넘으면 `ui-native` 승격을 검토한다"*고 적어 뒀고 이미 도감 내 3곳에서 쓰인다. 이 티켓이 4·5번째 사용처(동의 관리 실패, 신고 내역 실패)를 만든다 = **명백한 승격 신호**. 그러나 `packages/ui-native/src/index.ts` **export 추가 금지** 제약(MSG-420 소유, 이 티켓 유효)으로 **승격 불가**다. 따라서 이번에는 화면 로컬 복제로 가고 `nose.baseline.json`에 의도 중복으로 등재한다. **배럴 동결이 풀리는 시점의 1순위 승격 대상으로 기록한다** — 이 티켓이 만든 부채임을 리포트에 남긴다.

## 리스크

- **R1 (치명) 서버 계약이 티켓 요구와 정면 충돌** — 위치 동의 철회 불가(`false` → developCode 1400). 티켓 [동작 요구]의 한 축이 현재 API로 이행 불가능하다. Q1 미결 시 착수 불가.
- **R2 (구조) 철회 = 앱 전체 잠금** — `_layout.tsx`의 `AppShell`이 `locationConsent === false`에서 `Stack`을 `SignupConsentScreen`으로 대체한다(실측 B). 서버가 철회를 허용하게 되더라도 "설정에서 껐더니 앱이 회원가입 화면으로 잠긴다"는 결과는 그대로다 — API 추가만으로 해결되지 않는 **아키텍처 축 결정**이다.
- **R3 (외부 의존) 내 신고 내역 API 부재** — `/api/admin/reports`만 존재하며 관리자 전용 + 신고자 필터 없음. 호출 시 403이 정상이고, 만약 통과한다면 타인 신고 노출 사고다. **호출하지 않는다.** BE 환류 필요: `GET /api/users/me/reports`.
- **R4 (외부 의존) 약관 문구·API 모두 부재** — 5종 전부 자리표시. 화면·테스트·리포트 3중으로 미확정을 노출한다(위 방침 참조).
- **R5 (티켓 스테일) `report-types.ts` 부재** — 티켓 [참고]가 지목한 파일을 MSG-431이 삭제했다. 재사용 대상은 `features/video-actions/model/report.ts`다.
- **R6 (코드 주석 스테일) MSG-422 단언이 틀렸다** — `signup-consent.ts`·`use-update-location-consent.ts`·`signup-consent-screen.tsx` JSDoc이 *"저장할 서버 필드가 없다"*·*"서버에 저장 가능한 동의는 이 1건뿐"*이라 단언하는데, MSG-451 SDK 재생성으로 `submitConsents`(5항목 전부)·`updateMarketingConsent`가 생겼다. 이 티켓이 만지는 파일들이므로 **주석도 함께 정정**한다(정정하지 않으면 다음 티켓이 같은 오판을 승계한다).
- **R7 (사용자 관찰 가능 불일치) 가입 시 마케팅 동의가 저장되지 않는다** — MSG-422가 요청을 만들지 않으므로, 가입에서 마케팅에 동의한 사용자도 설정 화면에서 OFF로 본다. Q7 미결 시 이 불일치가 남는다.
- **R8 (병렬 충돌) MSG-447 동시 진행** — `setting-rows.tsx`는 이 티켓 소유이나 실제 변경 지점은 `profile-screen.tsx`다(Q6). 리베이스 순서 합의 필요.
- **R9 (부채) `DexErrorState` 승격 신호를 배럴 동결이 막는다** — 사용처가 5곳이 되는데 `ui-native/index.ts` export 금지로 로컬 복제 2벌이 늘어난다. 의도 중복 등재 + 후속 승격 대상 기록으로 처리한다.
- **R10 (인프라) RN 렌더 테스트 부재** — 화면에 남은 로직은 실기 검증 외에 안전망이 없다. 완화: 판정을 전부 순수 함수로 뽑는다(T1~T13). MSG-431의 오신고 회귀가 이 완화를 하지 않아 발생했다.
- **R11 (플랫폼) Hermes 미구현 API** — 신고 목록 정렬에 `toSorted`를 쓰기 쉽다. `oxlint no-restricted-properties`가 막지만(MSG-427 사고 후 도입) 설계 단계에서 `[...items].sort()`로 간다.
- **Figma 오탐 방지**:
  - 3화면 전부 **시안 부재**다(정본 페이지 `필맵 앱 디자인 MVP ver 6` 전수 검색). 검증에서 "Figma 대조 불일치"로 판정하지 말 것 — MSG-446 선례대로 "시안 부재 → 앱 관례 준수 감사"로 대체한다.

  - Figma의 진입 행 3종은 우측 라벨이 `준비 중 ›`(`14816:483`·`509`·`513`)이다. **이 티켓은 그 라벨을 의도적으로 제거한다** — 시안 대비 차이가 아니라 티켓의 목적이다.
