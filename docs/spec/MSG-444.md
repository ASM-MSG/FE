# MSG-444: [모바일] 카카오 로그인 실연동 — startKakaoLogin 스텁 교체

## 기획 요약
모바일 로그인 버튼이 no-op 스텁이라 토큰을 못 얻고, 그 탓에 인증이 필요한 화면 전부가 비어 있다.
카카오 인증 → 우리 토큰 발급 → 보안 저장소 저장 → 동의 게이트/홈 분기까지를 실제로 동작시킨다.
방식은 (A) 서버 주도 OAuth 재사용과 (B) 네이티브 카카오 SDK 중 택일이며, 아래 실측으로 **(B)를 확정**한다.
서버 엔드포인트 변경·타 소셜 제공자·이메일 로그인은 범위 밖이다.

---

## 방식 결정 — (B) 네이티브 SDK 확정

### 실측 1: 서버 계약 (2026-08-21, `https://api.fillmap.kr` 직접 호출)
```
GET /api/auth/oauth/kakao/authorize?redirectUri=fillmap://oauth/kakao/callback&state=probe123
→ 302
   Set-Cookie: OAUTH_NONCE=…; Path=/api/auth/oauth/kakao; Max-Age=600; Secure; HttpOnly; SameSite=None
   Location: https://kauth.kakao.com/oauth/authorize?client_id=…&redirect_uri=fillmap://oauth/kakao/callback
             &response_type=code&scope=openid&nonce=…&state=probe123
POST /api/auth/oauth/kakao/code   (쿠키 없이)
→ 401 {"developCode":2423,"message":"유효하지 않은 인가 코드입니다"}
```
서버는 커스텀 스킴 redirectUri를 그대로 통과시킨다(A의 전제는 성립). **문제는 nonce 쿠키다.**

### (A)가 막히는 지점
`POST /api/auth/oauth/kakao/code`는 `/authorize` 응답이 심은 `OAUTH_NONCE` **HttpOnly 쿠키**를 함께 받아야 한다
(생성 SDK 문서 원문: "인가 진입점이 심은 OAUTH_NONCE 쿠키가 함께 와야 한다(없으면 401)").
expo-web-browser로 `/authorize`를 열면 그 쿠키는 **인앱 브라우저(Chrome Custom Tabs / ASWebAuthenticationSession)의
쿠키 저장소**에 들어가고, 이어지는 POST는 앱 자신의 fetch 스택에서 나가므로 쿠키가 실리지 않는다 → 401.

우회 검토와 기각 사유:
- **RN에서 `/authorize`를 먼저 fetch해 쿠키를 앱 쿠키통에 담고 Location만 브라우저로 넘긴다** — RN의 fetch는
  XHR 기반이라 `redirect: "manual"`을 지원하지 않는다(리다이렉트를 강제로 따라간다). Location 헤더를 읽을 수 없다.
- **WebView로 전 과정을 처리해 쿠키통을 공유한다** — Android는 RN의 OkHttp가 `ForwardingCookieHandler`로
  WebView `CookieManager`와 같은 통을 쓰지만, iOS는 `WKHTTPCookieStore`가 분리돼 있어 성립하지 않는다.
  react-native-webview 신규 도입 + 임베디드 WebView 로그인이라는 비용도 크다.
- **서버가 콜백을 받아 토큰을 딥링크로 넘긴다** — 서버 엔드포인트 신설 = 티켓 제외 범위.

### (B)가 맞는 이유
생성 SDK의 같은 문서가 명시한다 — *"네이티브 SDK가 교환까지 해주는 앱은 이 API가 아니라
`POST /api/auth/oauth/{provider}`를 쓴다."* 앱 경로는 **백엔드가 이미 설계해 둔 계약**이고, 그 엔드포인트
(`oauthLogin`, body `{ idToken }`, `X-Client-Type: app`)는 생성 SDK에 이미 있다. 쿠키가 개입하지 않는다.
부가로 카카오톡 앱 전환 로그인(UX)까지 얻는다.

> 결론: (A)는 "UX가 조금 나쁜 대안"이 아니라 **서버 변경 없이는 완결되지 않는 경로**다. (B)로 간다.

### 실측 2: 패키지 선정 — `@react-native-kakao/{core,user}` 2.4.6 (2026-07-12)
- **Expo config plugin 내장** (`app.plugin.js` → `nativeAppKey` 옵션으로 AndroidManifest `kakao{appKey}` 스킴·
  iOS `CFBundleURLTypes` 자동 주입). 수기 네이티브 편집이 없다.
- `login({ nonce? })` 반환 타입에 `idToken?: string` 존재 → 서버가 요구하는 OIDC ID 토큰을 그대로 얻는다.
- TurboModule spec 보유(신아키텍처 대응) · 제작자가 이미 쓰고 있는 `@mj-studio/react-native-naver-map`와 동일.
- `getKeyHashAndroid()` 제공 — 콘솔에 등록할 키 해시를 실기에서 직접 확인할 수 있다.
- 대안 `@react-native-seoul/kakao-login` 6.0.4는 Expo config plugin이 없어 prebuild 파이프라인에 수기 패치가 필요 → 기각.

### 실측 3: OIDC 활성 여부
`/authorize`가 조립한 카카오 인가 URL에 `scope=openid`·`nonce`가 들어 있고 서버가 ID 토큰 교환을 수행한다
= 해당 카카오 애플리케이션에 **OpenID Connect가 이미 활성**돼 있다(앱 단위 설정이라 네이티브 앱 키에도 적용).
따라서 네이티브 SDK 로그인도 `idToken`을 받을 수 있다. 만약 받지 못하면 기준 5가 그 사실을 즉시 드러낸다.

## 추정 및 질문

- **Q1 (핵심)**: 방식을 **(B) 네이티브 SDK**로 확정한다. 근거는 위 실측 — (A)는 nonce 쿠키가
  인앱 브라우저 저장소에 갇혀 서버 변경 없이는 완결 불가. **승인 필요.**
- **Q2**: 콘솔 등록 담당은 사용자. 필요한 값은 위 목록에 정리했다. 등록 전이면 기준 9~16은 "확인불가"로 남는다
- **Q3**: env 변수명을 `EXPO_PUBLIC_KAKAO_NATIVE_APP_KEY`로 한다(네이버 키 명명 관례 승계).
  네이티브 앱 키는 클라이언트 공개를 전제로 한 키(패키지명+키 해시로 보호)라 `EXPO_PUBLIC_` 노출이 정상이다
- **Q4**: `login()`에 `nonce`를 넘기지 않는다. 네이티브 경로의 서버 검증은 ID 토큰 자체 검증이고 대조할
  저장 nonce가 없다(쿠키를 심는 쪽은 `/authorize` 경로뿐). 난수 생성용 `expo-crypto` 신규 의존도 피한다
- **Q5**: `use-dev-login`은 **존치**한다. 지금도 `/dev/api-smoke`에서만 도달 가능하고 로그인 화면에 노출되지
  않으며, 콘솔 등록 전/CI 환경에서 토큰을 얻는 유일한 경로다. 로그인 화면에 붙이지는 않는다
- **Q6**: `kakao-login.ts`와 그 테스트는 삭제한다(책임이 두 파일로 갈림). 티켓의 "교체 지점은 함수 하나"와
  형식이 다르지만, 훅 테스트 불가 문제(MSG-426)를 피하려면 옵션 팩토리 분리가 필요하다
- **Q7**: iOS는 config plugin 설정만 넣고 **검증하지 않는다**(Android 우선, 실기가 Android뿐).
  플러그인이 `CFBundleURLTypes`를 채우므로 iOS 빌드가 깨지지는 않는다

## 실기 검증 결과 (갤럭시 S25, 카카오톡 설치)

**카카오 로그인 자체는 동작한다.** 버튼 탭 → 카카오톡 앱 전환 → ID 토큰 수령까지 실기에서 확인했다(기준 9 통과).
기준 8도 실런타임으로 실증됐다 — Metro가 `@react-native-kakao/*`를 **앱 기동 시가 아니라 버튼 탭 시점에** 번들했다.
기준 14(실패 안내 + 재시도)도 통과. **막힌 곳은 우리 서버다.**

```
POST /api/auth/oauth/kakao (X-Client-Type: app)
→ 401 { developCode: 2421, "유효하지 않은 소셜 로그인 토큰입니다" }

수령 ID 토큰: iss=https://kauth.kakao.com, aud=73558381b47d1b7c53b551a7596c56cf(네이티브 앱 키), sub 정상
서버 검증 기준: ef9572baf11b76a88097eeea6287d786(REST API 키 — /authorize의 client_id에서 실측)
```

카카오는 인가를 요청한 앱 키를 그대로 `aud`에 넣는다. 웹은 REST 키, 앱은 네이티브 키라 갈린다.
`nonce`는 배제 완료(클레임을 실어도 동일한 2421). **클라이언트 우회 경로는 없다** — `aud`는 SDK 초기화 앱 키로
카카오가 정하고, 네이티브 SDK에 REST 키를 넣는 것은 카카오가 거부한다.

**BE 요청**: `POST /api/auth/oauth/{provider}`의 OIDC 검증에서 네이티브 앱 키를 유효한 `aud`로 허용할 것.

검증이 개선 1건도 잡았다 — `developCode 2421`이 매핑에 없어 "다시 시도해 주세요"로 떨어졌는데, 이건 다시 눌러도
절대 안 풀리는 실패다. 재현 테스트 후 `misconfigured`("설정에 문제가 있어요")로 매핑했다(모바일 전용 축, parity 무영향).
