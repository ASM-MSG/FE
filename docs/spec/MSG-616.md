## 기획 요약

앱이 영상을 서버로 보내기 전에 기기 하드웨어 인코더로 **세로 720 이하 · H.264 · AAC** MP4로 변환한다. 촬영본·갤러리본 모두 대상이고, 변환 중 진행 표시가 있어야 하며, 실패하면 원본으로 업로드를 이어간다(서버가 기존 인코딩 경로로 처리). BE 짝 티켓 MSG-615가 이 조건의 입력을 `-c copy -movflags +faststart`로 remux하므로, 조건이 맞으면 서버 처리가 3초 안에 끝난다. 네이티브 모듈이 들어가므로 1.0.1 스토어 빌드에 포함한다. 비스코프: 서버 변경·화질 옵션 UI·웹 업로드.

## 코드·계약 실측 (스펙 근거, 2026-10-03)

- **BE 현행 인코딩**(`BE origin/develop` `FfmpegRunner.encode720p`): `-vf scale=-2:720 -c:v libx264 -preset veryfast -crf 23 -c:a aac -b:a 128k -movflags +faststart`. **세로(height) 720 고정, 가로는 비율**이다 — ffmpeg autorotate가 기본이라 세로 촬영본(코딩 1920×1080 + rotate 90)은 1080×1920으로 돌려진 뒤 **406×720**으로, 가로 영상은 1280×720으로 나온다(`FfmpegRunnerTest`: "1080p를 1280x720 h264로 변환한다").
- **BE remux 게이트**(MSG-615 원문, 브랜치 아직 없음): `ffprobe -show_streams`로 **비디오 h264 && height ≤720 && 오디오 aac 또는 없음**. faststart는 remux 출력 쪽에서 붙인다 — **입력 조건이 아니다**.
- **모바일 업로드 흐름**(`apps/mobile/src/features/upload`): `/upload`(선택) → `/upload/analyzing`(선분석: presign(HIGHLIGHT_PREVIEW)→**원본 S3 PUT**→`highlight-preview`) → `/upload/highlight` → `/upload/preview`(확정: presign(UPLOAD)→**원본 S3 PUT**→`POST /api/videos`). **같은 파일을 두 번 올린다.** 두 레인 모두 `uploadFlowStore.video`(`UploadVideo {uri, durationSec, fileName, fileSize, mimeType}`)에서 `UploadSource`/`ConfirmUploadInput`을 조립한다(`analyzing-screen.tsx:72`, `confirm-input.ts buildConfirmInput`). `durationSec`(확정 body)은 선택 구간 길이, `fileSize`는 presign `contentLength`, `mimeType`은 presign `contentType`·S3 PUT 헤더.
- **S3 PUT**(`api/s3-upload.ts`): `fetch(fileUri)` → `arrayBuffer()` → PUT. `file://` 경로를 그대로 읽을 수 있다.
- **영속**(`upload-flow-store.ts` `PersistedUploadFlow` 9필드, `upload-flow-storage.ts` 형상 검증 `isVideo` — `uri·fileName` 필수, 나머지 null 허용 / `upload-flow-persistence.ts` AsyncStorage 배선 / `upload-flow-resume.ts` 콜드 스타트 복귀 라우트). 구버전 저장값 하위호환은 `eventTarget`·`visibility` 패턴("필드 없음 → 기본값 정규화, 있는데 형상 불량 → 진행 없음").

### 라이브러리 실측 (react-native-compressor 2.0.3, 2026-07-25 · GitHub main)

- JS: `Video.compress(fileUrl, {compressionMethod:'manual'|'auto', maxSize, bitrate?, progressDivider?, getCancellationId?}, onProgress(0~1)) → Promise<string>`(출력 `file://…/<uuid>.mp4`, Android는 `cacheDir`, iOS는 `NSTemporaryDirectory`), `Video.cancelCompression(id)`, `getVideoMetaData(path) → {size(bytes), duration(sec), width, height, extension}`.
- **크기 정책**: `scaleWithin`이 **긴 변**을 `maxSize`로 맞춘다(iOS `VideoMain.swift:173`, Android `VideoCompressionProfile.kt:82`). Android는 rotate 90/270 소스를 **폭·높이 교환 후 rotation 0으로 굽고**(`Compressor.kt:147`), iOS도 `videoComposition.renderSize`를 교환해 **코딩 자체가 세로**로 나온다(`NextLevelSessionExporter.swift:533`). 즉 출력에 회전 태그가 없고 ffprobe `height` = 표시 높이.
- **코덱**: 비디오 `video/avc`(Android, 하드웨어 인코더 우선·QTI 결함 코덱 회피) / `AVVideoCodecType.h264` High(iOS). 오디오 iOS **AAC 128k 44.1k 재인코딩**, Android **패스스루**(소스 트랙 복사 — 폰 촬영본은 AAC).
- **faststart**: Android `StreamableVideo.start`가 모든 출력에 moov를 앞으로 옮김(`Compressor.kt:563`), iOS `optimizeForNetworkUse = true`(`VideoMain.swift`). 둘 다 켜져 있다.
- **메타 누락 시 실패**: Android는 rotation/bitrate/duration 메타가 없으면 "Failed to extract video metadata"로 reject → 원본 fallback 경로.
- **아키텍처**: 2.0.0부터 **nitro 모듈**(`react-native-nitro-modules >=0.35.0` peer, 최신 0.37.1 2026-08-27) — New Architecture 전용. RN 0.75+/iOS 13.4+/Android 24+. Expo config plugin `app.plugin.js`는 **no-op**(등록만 하면 됨). 네이티브이므로 `expo prebuild` + dev client 재빌드 필수.
- **성숙도**: ★1,338 · 월 86만 다운로드 · 최근 푸시 2026-07-25 · 이슈 30.

## 리스크

- **R1 BE 게이트 의미론 의존**: MSG-615가 "세로 ≤720"을 ffprobe **코딩 height**로 구현한다는 티켓 원문에 맞춰 D2를 정했다. BE가 구현 중 `min(w,h)`나 표시 크기로 바꾸면 `transcodeMaxSize`만 바꾸면 된다(순수 함수 1곳). **환류**: BE에 "FE 출력은 회전 태그 없는 코딩 세로 406×720 / 가로 1280×720"을 알린다. MSG-615 브랜치가 아직 없어 dev 서버 remux 실측(처리 <3s)은 BE 머지 전엔 불가 — AC 2는 ffprobe로 닫는다.
- **R2 nitro ↔ Expo 57/RN 0.86 미실측**: nitro 0.37.1(2026-08)이 RN 0.86(2026-10)에서 prebuild·Gradle·CocoaPods가 통과하는지 확인된 바 없다. 실패 시 ① nitro 최신/next 태그 ② compressor 1.19.4(구 브릿지 — New Arch interop 의존, RN 0.86에서 더 불안) ③ `expo-image-and-video-compressor` 대체 순으로 재판단하고 스펙 D1 갱신.
- **R3 검증 환경**: 새 네이티브 의존성 → **prebuild + dev client 재빌드 필수**(런북 2-1). 구 dev client로 돌리면 D6 fallback이 조용히 원본 업로드를 성공시켜 "구현됨"으로 오판할 수 있다 → 검증자는 Metro 로그 `[transcode] done`을 반드시 확인. **10초 기준(AC 6)은 실기기 전용** — 에뮬레이터 MediaCodec은 소프트웨어 인코더라 수치가 수 배 느리다(기능 확인·ffprobe만 에뮬레이터 가능).
- **R4 Android 오디오 패스스루**: 갤러리본이 비-AAC(opus·mp3 등)면 변환본도 비-AAC → BE 게이트 탈락 → 기존 인코딩 경로(안전, 느림). 폰 촬영본은 AAC라 주 경로엔 영향 없음. iOS는 재인코딩이라 항상 AAC.
- **R5 Android 메타 누락 reject**: 일부 갤러리 파일(rotation/bitrate 메타 없는 리먹스 파일)은 라이브러리가 즉시 실패 → D4 fallback(원본 업로드). 티켓 허용 범위.
- **R6 캐시 파일 수명**: 변환본은 OS 캐시 디렉터리라 세션 사이에 회수될 수 있다. 재개 시 파일이 없으면 기존 `s3put` 단계 실패 문구("영상 업로드에 실패했어요") + [다시 시도]가 뜨고 계속 실패한다 — 사용자는 [이전으로]로 재선택. 원본 `content://`·picker 캐시도 같은 노출이 이미 있어 **새 리스크 폭은 작다**. 완화 코드 없음(YAGNI, 재발 시 환류).
- **R7 iOS `getVideoMetaData.size` 타입**: iOS 소스가 `fileSizeString` 변수명이라 문자열일 가능성 → `Number()` 변환, 비유한이면 fallback(D7). iOS 실기는 이번 검증 범위 밖(Android 우선) — 코드 리뷰로만 닫힘.
- **R8 빌드 번호·OTA**: 1.0.2 첫 빌드(iOS 1 · Android versionCode 2)로 올린다(D10). fingerprint 분기로 1.0.1 빌드 4/5 사용자는 이 JS를 OTA로 받지 않는다 — 의도. 1.0.2는 묶음 후보가 더 쌓일 수 있어 **이 티켓 단독으로 빌드하지 않는다**(보류 상태).
- **R9 긴 영상 체감**: 180초 영상은 변환 ~1분. 진행 바가 실값이라 멈춤으로 보이진 않지만 총 대기(변환+업로드+분석)가 늘어난다. 업로드가 1/10로 줄어 순 대기는 감소 — 실기 로그로 확인.
