# MSG-408: FCM 웹 푸시 기반 구축 · 푸시 토큰 연동

> **v2 (2026-08-17)** — 사용자 승인 게이트 결정 반영: ① 권한 요청 UX = 프로필 "알림 받기" 토글 방식(셸 렌더 시 자동 프롬프트 폐기), ② Firebase config·VAPID 공개키 = 코드 상수 커밋(**VITE_ env 컨벤션의 명시적 예외 — 사용자 승인, 2026-08-17**).

## 기획 요약
Firebase SDK 초기화 + `firebase-messaging-sw.js` 서비스 워커 + 알림 권한 요청 UX로 FCM 웹 푸시 기반을 구축한다. 알림 opt-in은 프로필 설정의 "알림 받기" 토글로 한다(결정 1) — 토글 ON 시 사용자 제스처 컨텍스트에서 권한 요청 → `getToken(VAPID)` → `POST /api/notifications/tokens {fcmToken, platform: "WEB"}` 등록(UPSERT 멱등), 토글 OFF 시 `DELETE /api/notifications/tokens`. 이미 등록된 사용자는 셸 렌더 시 자동 동기화(재등록·로테이션). 로그아웃은 기존 `/api/auth/logout` body에 `fcmToken` 동봉(토큰 해제 겸). 포그라운드 수신은 `onMessage` → 토스트(기존 "블러 완료 알림" 패턴 재사용). VAPID 공개키·Firebase 웹 config는 티켓 description에 전량 수급 완료(`_workspace/MSG-408/00_ticket.md` "키/설정" 절 — 정본은 지라).

| 8 | 푸시 미지원 브라우저(Notification·serviceWorker·PushManager 부재)에서 토글 행은 조작 불가(비활성) 안내 상태이고, 자동 동기화도 스킵되며 콘솔 에러·크래시가 없다 | 로직 | vitest (지원 판별 순수 함수) |
| 9 | 로그아웃 시 보관된 fcmToken이 있으면 `/api/auth/logout` body에 `{fcmToken}`을 동봉하고, 성공·실패 무관 로컬 보관 토큰을 비운다. 보관 토큰이 없으면 기존과 동일하게 body 없이 호출한다 | 로직 | vitest (useLogout 기존 테스트 확장) |
| 10 | 포그라운드에서 `onMessage` 수신 시 우하단 토스트로 알림 제목·본문이 표시되고 닫을 수 있다 (UploadProcessingNotices와 같은 스택 관례) | 화면 | vitest 스모크 (onMessage 모킹) + 브라우저 육안 1회 |
| 11 | `firebase-messaging-sw.js`가 `apps/web/public/`에 존재해 dev·빌드 산출물 루트에서 서빙되고, 토큰 취득 경로에서 이 SW가 등록되어 dev 서버(localhost:5173)에서 등록 성공·콘솔 에러 없음이 확인된다 | 화면(스모크) | 브라우저 (Application > Service Workers + 콘솔) |
| 12 | 서비스 워커는 env 변수 없이 동작한다 — Firebase config는 앱이 SW 등록 URL 쿼리스트링으로 전달하고, config·VAPID 정본은 코드 상수 모듈 1곳이다(중복 선언 없음). **코드 상수 커밋은 VITE_ env 컨벤션의 명시적 예외(사용자 승인, 2026-08-17)** | 로직 | 코드 감사 + vitest (URL 조립 순수 함수) |
| 13 | 등록·해제 API 실패(네트워크·5xx)가 앱 기동·로그인·프로필 화면 흐름을 막지 않는다 — 자동 동기화 실패는 콘솔 경고로만 남고, 토글 조작 실패는 토글 상태가 실제 결과와 어긋나지 않게 반영된다 | 로직 | vitest |

**검증 프로파일**: 화면 — v2에서 프로필 설정에 신규 인터랙티브 UI(알림 받기 토글 행)가 생겨 로직+화면 혼합 → 넓은 쪽 판정. 단 Figma 노드 없는 인프라 티켓이라 Figma 대조는 비대상이고, 브라우저 검증 범위는 프로필 토글 행(상태 전환·denied 안내·a11y) + SW 등록·포그라운드 토스트·콘솔 스모크로 한정한다. 백그라운드 푸시 **실수신** E2E는 BE 발송 수단이 필요해 검증 범위에서 제외(리스크 참조).

## 리스크

- **결정 1의 전제와 코드 불일치(해소됨)**: "MSG-407 프로필 위치동의 토글 재사용" 전제는 실제 코드와 다름 — 해당 토글은 MSG-407 v3 결정으로 제거됐고 ProfilePanel에는 비활성 행만 남아 있다. 이 스펙은 실존 관례(ui-web Switch + SettingRow + use-profile-mutations 패턴)로 대체 반영했다 — 구현 착수 전 재확인 불필요.
- **실수신 E2E 불가**: 백그라운드/포그라운드 실제 푸시 수신은 BE(또는 Firebase 콘솔)의 발송이 필요 — 이 티켓 검증은 토큰 등록/해제 API 왕복·SW 등록·onMessage 모킹까지. 실발송 검증은 BE 합동 확인 사항.
- **토글 ↔ 실제 등록 상태의 어긋남 가능성**: 서버 등록 성공 후 보관 저장 전 이탈 등 엣지에서 정본(granted && 보관 토큰)과 서버 상태가 어긋날 수 있음 — UPSERT 멱등·DELETE 멱등이라 다음 조작·자동 동기화에서 자기 수복된다는 전제. 기준 13이 어긋남 최소화를 커버.
- **SW의 CDN importScripts**: gstatic CDN 의존(앱 본체는 npm 번들, SW만 CDN). 차단 환경에서 SW 초기화 실패 가능 — 백그라운드 표시만 영향, 앱 본체 무영향.
