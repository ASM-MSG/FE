# MSG-473: 코스 미션 경로 — 서버 LineString 객체 수용 + 스팟 직선 폴백 제거

## 기획 요약

코스 미션의 `shape.line`이 서버에서 GeoJSON **객체**(`{type:"LineString",coordinates:[[lng,lat],…]}`)로 오는데, FE가 `typeof shape.line === "string"` 체크로 null로 버려 실제 답사 트랙 대신 포토스팟 1→2→3→4 직선을 그린다(만을 가로지름). 객체·문자열 어느 쪽이 와도 라인을 그리도록 두 파싱 지점을 고치고, MSG-403 후속으로 넣었던 "라인 없으면 스팟 순 직선" 폴백은 **제거**한다(사용자 승인 완료 — 스팟은 촬영 지점이지 이동 경로가 아니다). 웹·모바일 동시 수정(parity 테스트가 한쪽 수정을 깨뜨린다).

**dev 실측 (이번 스펙 단계, 익명 curl 200)**: `GET /api/missions/active?type=COURSE&swLat=35.05&swLng=128.95&neLat=35.2&neLng=129.1` → 코스 2건, `shape.line`은 `typeof === "object"`·`type: "LineString"` — 남파랑길 3코스(missionId 395) 114점·spots 6, 4코스(396) 170점·spots 8. 티켓 기대값과 일치.

**부수 실측 3건 (계획에 반영):**
- **PATH bbox가 스팟만으로 계산됨** (`mission.ts` `fromGridPoints` — `boundsOf(points=spots)`): 실 데이터에서 라인이 스팟 bbox를 **최대 1.33km 초과**(3코스 남 0.84km·동 0.79km, 4코스 북 1.33km·동 1.10km). 코스 선택 fitBounds(`MapHomePage.tsx:213` — `shape.bbox` 사용)와 뷰포트 필터(`mission-overlay.ts:20 missionsInBounds`)가 이 bbox를 쓰므로, 라인 기준으로 확장하지 않으면 실경로 끝단이 화면·필터 밖으로 잘린다. 티켓 "fitBounds 대상 등 기존 파생은 실제 라인 기준으로 그대로 동작" 요구의 실측 귀결.
- **모바일 라인 없는 코스의 번호 마커 소실**: `use-home-overlays.ts:134` — `path.length === 0`이면 `route` 전체를 undefined로 만들어 waypoints(번호 마커)까지 사라진다. 폴백 제거 후 "라인 없으면 번호 마커만"을 만족하려면 이 가드를 path만 비우는 것으로 조정 필요. (웹 `buildCourseRoutes`는 path가 비어도 waypoints를 항상 담아 이미 올바름 — `mission-overlay.test.ts:191~192`가 단정)
- **생성 타입 캐스팅은 불필요**: `PathShape`(`apps/web/src/shared/api/generated/types.gen.ts:1782` — `line: string | null`)의 소스 소비처는 **0건**(주석 언급뿐). `missionShapeOf`는 `mission.shape`를 `unknown`으로 받아 `isRecord`로 좁히므로 `shape.line`은 이미 `unknown` — `MissionShape.line` 타입만 넓히면 되고 `as` 캐스팅 지점이 생기지 않는다. **`api:generate` 재생성 금지**(병렬 티켓과 생성물 충돌 — BE MSG-472가 명세 정정, 재생성 시 자연 수렴).

**렌더링은 무변경**: 웹 `MapCanvas.tsx:691`(`route.path.length > 1`일 때만 Polyline)·모바일 `grid-map.tsx:396`(`route.path.length >= 2`) 가드가 이미 있어 파싱만 고치면 그대로 그려진다. 번호 마커는 양쪽 모두 spots에서 파생(웹 `buildCourseRoutes` waypoints / 모바일 `buildRouteWaypoints(spots)`)이라 114점 라인이 마커 114개가 되지 않는다.

## 리스크

- **MSG-403 폴백 제거의 배경과 번복 리스크**: 직선 폴백은 MSG-403 검증 후 사용자 추가 요구였다 — 당시 실 데이터 코스는 라인이 비어 있어 번호 마커만 흩어져 순서를 읽을 수 없었다(docs/spec/MSG-403.md 추가 요구 1). 지금은 dev 코스 148건 전부 line 보유(BE 확인)라 전제가 뒤집혔다. 잔여 리스크: 향후 line 없는 코스가 등록되면 선 없이 마커만 보인다 — 티켓이 명시 승인한 동작이므로 결함 아님.
- **스테일 문서**: `docs/spec/MSG-427.md` E14와 MSG-403 스펙이 직선 폴백을 정본으로 기술 — 과거 스펙은 이력이므로 수정하지 않고, 이번 스펙·STATUS.md 한 줄이 번복을 기록한다. 코드 주석(course.ts·mission-view.ts의 "MSG-403 후속"/"E14" 언급)은 함께 갱신.
- **명세-실서버 불일치(의도됨)**: 생성 타입 `PathShape.line: string | null` vs 실응답 객체 — BE MSG-472가 정정. 이번 티켓에서 `api:generate` 실행 금지(병렬 티켓 생성물 충돌). 검증 게이트에 "생성물 diff 0" 포함.
- **parity 절단면**: 웹만 또는 모바일만 고치면 `course.parity.test.ts`·`mission.parity.test.ts`가 즉시 깨진다 — 4파일 대칭 수정이 한 커밋에 있어야 한다. 모바일은 Hermes 제약(`toSorted` 등) 유지 — oxlint no-restricted 룰이 기계 차단.
- **익명 API 개방 실측**: 위 dev curl이 **익명 200**(MSG-403 당시 401) — 검증 시 API 확인은 비로그인으로도 가능하나, FE 미션 쿼리 게이트(비로그인 미발사)는 이 티켓 범위 밖이므로 브라우저 검증은 로그인 세션으로 수행.
- **Figma 오탐 방지**: 이 티켓에는 Figma 노드가 없다(데이터 형상 버그). 코스 라인의 형상 기준은 dev 실응답 좌표(3코스 114점·4코스 170점 해안선)이며, 디자인 대조 대상이 아니다. 번호 마커 스타일은 무변경(기존 정본 유지).

### 검토한 대안 (기각 사유)

- **`coursePath` 삭제하고 호출부가 `parseLineString`을 직접 호출** — 기각. AC 5·parity 테스트가 함수명을 계약으로 지목하고, "지도에 그릴 경로"라는 의미와 MSG-403 번복 사유를 담을 문서화 지점이 사라진다.
- **깨진 픽스처마다 `as unknown as` 캐스팅** — 기각. FE 런타임 계약이 명세보다 넓다는 사실(문자열 원문·깨진 형태까지 방어 흡수)이 테스트의 목적 자체라, 헬퍼 한 곳에서 의도를 주석과 함께 밝히는 쪽이 소급 가능하다. `& { shape?: unknown }` 교집합은 `T & unknown = T`라 무효 — `Omit` 선행이 필수임을 1차 시도로 실측.
- **`MissionShape.line`을 `string | Record<string, unknown> | null` 유니온으로 명시** — 기각. 소비처가 `parseLineString` 하나뿐이라 `unknown`이 더 좁은 표면을 노출하고, BE 명세가 어느 쪽으로 확정되든 FE 무변경으로 수렴한다.
- **bbox 확장을 fitBounds 호출부에서만 수행** — 기각. `shape.bbox`를 fitBounds·`missionsInBounds`·이름표 중심이 공유하므로 `missionShapeOf` 한 곳에서 확장하는 쪽이 일관적이다(이름표 중심이 수백 m 이동하는 부작용은 승인된 결과).
