# MSG-551: 관리자 계정 운영 — 운영자 계정 발급 · 발급 요청 큐 · 이메일 변경 큐 · 비밀번호 재발송

## 기획 요약

관리자가 행사 운영자 계정의 수명주기를 다루는 `/admin/accounts` 화면. ① 공문 확인된 기관에 계정을 직접 발급하고(초기 비밀번호는 서버가 공식 이메일로 발송 — **화면 절대 비노출**), ② 기관이 보낸 계정 발급 요청을 승인/반려하며(반려 사유 필수), ③ 아이디(이메일) 변경 요청을 승인/반려하고, ④ 초기 로그인 전 계정에 비밀번호를 재발송한다. 행사 심사(552~554)·운영자 쪽 폼(543·544)은 제외 범위다.

웨이브 2 (선행 MSG-541·웨이브 1 머지됨, 병렬: MSG-547·549·543·544). **`app/router.tsx`·`app/console-routes.ts`·`shared/api/generated/**` 수정 금지, `widgets/console-shell`·`console-config` 무수정 우선(질문 1), 병렬 티켓 소유 파일 비접촉, `console-routing.smoke.test.tsx`는 자기 1줄만. 이 티켓 소유 스텁 = `pages/admin/AdminAccountsPage.tsx` 1개 + 신규 feature 디렉토리.**

## 코드베이스·API 대조 결과 (스펙의 전제 — 전부 2026-09-04 실측)

- **직접 발급** `issueDirect`(POST /api/admin/organizations, `issueDirectMutation` 존재). body `OrgAccountCreateRequestDto` = `orgName`(필수)·`contactName`(필수, 2~20자)·`email`(필수 — 계정 아이디이자 초기 비밀번호 수신처)·`contactPhone?`(선택, 숫자 시작·끝 숫자·하이픈 9~20자). 응답 `OrgAccountIssueResponseDto { userId, emailSent }` — **초기 비밀번호는 어떤 응답에도 없다**(서버 재료 확정). `emailSent`는 SES 접수까지의 성공(배달 확인 아님). 이미 계정이 있는 이메일은 409(**1409**). SDK doc: 응답 유실 시 재시도 → 1409면 계정 목록 email 검색으로 발급/충돌을 가른다.
- **계정 목록** `getAccounts`(GET /api/admin/organizations, `getAccountsOptions` 존재). query `page?`(0부터)·`size?`(1~100)·`email?`(완전 일치 검색). 응답 `AdminOrgAccountListResponseDto` = totalElements·page·size·`accounts[]`(발급 최신순 고정). 항목 = `userId`·`orgName|null`·`contactName`·`email`·`contactPhone|null`·`provider`(LOCAL만 담김)·**`mustChange`**(true=초기 로그인 전 / false=사용 중 — 서버 doc이 이 라벨을 명시)·`createdAt`. page 음수·size 범위 밖 400(1425).
- **재발송** `resendPassword`(POST …/{userId}/resend-password, `resendPasswordMutation` 존재). body 없음. 응답 `{ emailSent }`. **재발송 = 재발급**(새 초기 비밀번호 생성·이전 것 즉시 무효). 대상은 초기 로그인 전(mustChange=true) 계정뿐 — 이미 변경한 계정 409(**1423**, 분실 복구는 비밀번호 재설정 흐름 안내), 없는 사용자 404(**1404**).
- **발급 요청 큐** `getRequests`(GET /api/admin/org-account-requests, `getRequestsOptions`). query `status?`(PENDING·ISSUED·REJECTED, 기본 PENDING)·page·size. 응답 = **`pendingCount`/`issuedCount`/`rejectedCount`(필터 무관 전체 집계 — 탭 뱃지용)** + totalElements·page·size + `requests[]`(**마지막 접수(updatedAt) 최신순 고정**). 항목 = id·orgName·contactName·email·**eventName**(예정 행사명)·status·createdAt·updatedAt.
- **요청 상세** `getRequest`(GET …/{requestId}, `getRequestOptions`). 항목 필드 전체 + `contactPhone`·**`content`**(요청 내용)·`rejectReason|null`·`issuedUserId|null`·`processedAt|null`. **응답의 `updatedAt`이 승인·반려에 그대로 에코해야 하는 검토 기준 시각**이다. 없는 요청 404(1421).
- **승인** `approve1`(POST …/approve, `approve1Mutation`). body `OrgAccountRequestApproveRequestDto { updatedAt }`(상세의 값 에코). 응답 = `OrgAccountIssueResponseDto { userId, emailSent }` — 직접 발급과 동일 결과. 메일 실패해도 계정·ISSUED 유지(emailSent=false, 복구는 재발송). 에러: 404(**1421**)·409(**1422** 이미 처리/동시 승인 늦은 쪽)·409(**1426** 검토 이후 내용 변경)·409(**1409** 이메일 충돌).
- **반려** `reject2`(POST …/reject, `reject2Mutation`). body `OrgAccountRequestRejectRequestDto { reason(필수, 최대 500자), updatedAt }`. **메일은 발송되지 않는다** — 반려 통보는 수기이고 저장 사유가 재료. 에러: 1421·1422·1426.
- **이메일 변경 큐** `getEmailChangeRequests`(GET /api/admin/email-change-requests, `getEmailChangeRequestsOptions`). query `status?`(PENDING·APPROVED·REJECTED, 기본 PENDING)·page·size. 응답 = `pendingCount`/`approvedCount`/`rejectedCount`(필터 무관) + totalElements 등 + `requests[]`. 항목 = id·userId·`orgName|null`·**`email`(현재 아이디)와 `requestedEmail`(바꾸려는 이메일)이 나란히**·status(union)·**`createdAt`(검토 기준 시각 — 재요청이 같은 대기 행을 덮어쓰므로 이 값 에코가 사고 방지)**·processedAt|null·rejectReason|null. **상세 API 없음 — 목록 항목이 상세 전체다.**
- **이메일 변경 승인** `approveEmailChange`(body `{ requestedAt }` = 목록 createdAt 에코). 응답 `{ requestId, email, emailSent }` — 아이디 교체 + **새 이메일로 변경 완료 통지**(발송 실패해도 교체 유지, emailSent=false). 에러: 404(**1427**)·409(**1428** 이미 처리)·409(**1429** 검토 이후 변경)·409(**1409**). **반려** `rejectEmailChange`(body `{ requestedAt, reason(필수) }`) — 메일 미발송·수기 통보, 에러 1427·1428·1429.
- **콘솔 기반(MSG-541)**: `/admin/accounts` 라우트·`RequireAdminRole` 가드·셸 완비. 스텁 `AdminAccountsPage.tsx`(`ConsoleStub title="계정 운영"`)만 교체. **관리자 사이드바에 `/admin/accounts` 메뉴가 없다**(console-config 실측: `ADMIN_CONSOLE.menu` = 행사 심사·승인 행사 2개뿐) — 도달은 레일 "계정" 섹션(path=adminAccounts)이고, 이 화면에서 사이드바 활성 강조 공백은 MSG-541의 알려진 구조다. ### Figma 실측 (15525:9064 발급 · 15579:2326 요청 큐)

두 노드는 **사이드바 메뉴로 분리된 별개 화면 2장**이다(발급 요청 / 운영자 계정). 이메일 변경 큐 시안은 **없다**.
- **운영자 계정(9064)**: 헤더 "행사 운영자 계정 발급"+설명("공문·오프라인 문의가 완료된 기관에 LOCAL 로그인 계정을 발급합니다."). 좌 카드 "새 계정" = 기관명·담당자·공식 이메일 인풋 3개(연락처 없음) + "초기 비밀번호 전달" 행("공식 이메일로 자동 발송 · 24시간 내 변경 필요" + [비밀번호 재발송] 버튼) + 안내 박스("기관이 보낸 계정 발급 요청은 '발급 요청' 화면에서 확인·처리") + CTA "행사 운영자 계정 발급". 우 카드 "최근 발급" = 기관/상태 2열 행 목록, 행 = 기관명 + 캡션 `provider=LOCAL` + 상태("사용 중" green / "초기 로그인 전" blue).
- **발급 요청(2326)**: 헤더 "계정 발급 요청"+설명. 상태 pill 3종(대기 3 활성 채움 · 발급됨 12 · 반려 1). 좌 카드 "대기 요청" 테이블(기관·담당자·요청 행사·요청일("오늘 09:12"식)·상태(대기 amber 칩), 선택 행 좌측 블루 바). 우 카드 "선택한 요청" = 요청 내용 박스 · 요청 기관(기관명/담당자·연락처/이메일) · 예정 행사("2026 부산 바다축제 · 9.5–9.7") · [요청 상세 보기] · [반려](outline red)+[계정 발급](primary) · 각주 "발급 시 공식 이메일로 초기 비밀번호가 발송됩니다".
