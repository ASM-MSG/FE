# MSG-445: [모바일] 실기기 API 연동 전 구간 점검 — 로그인 후 인증 API 실측

## 기획 요약

웨이브 0~3(MSG-419~431)이 넣은 모바일 API 연동을 **실기기에서 로그인된 상태로 처음으로 끝까지 돌려보는 점검 티켓**이다. 선행 MSG-444(카카오 로그인 실연동, 머지 8b07d3d)로 실 토큰을 얻을 수 있게 됐으므로, 7개 화면군을 순회하며 "실 서버 응답이 화면에 안 뜬다"는 지점을 찾아 원인을 클라이언트/서버/계약 불일치로 분류한다. 산출물의 본체는 **화면별 판정표**(7개 화면군 × 로딩·빈 결과·조회 실패)이고, 코드 수정은 부산물이다.

**이 티켓의 성격**: 신규 기능 구현이 아니라 점검(QA) 티켓. 정적 게이트(vitest·typecheck·lint)만으로는 통과할 수 없고, 본질은 갤럭시 S25 실기 실측이다.

## 선행 완료 작업 — hey-api 계약 점검 (스펙 작성 전 수행 완료, 판정표 1행에 기록할 것)

티켓의 "계약 불일치" 원인 후보를 먼저 소거하기 위해 서버 명세 최신화를 완료했다:

- `apps/web/openapi/api-docs.json` 스냅샷 갱신: **diff 있음** — 신규 엔드포인트 2개 추가(`POST /api/routes/recommend` 경로 추천, `GET /api/hotzones/aggregation` 핫존 집계). **기존 엔드포인트/DTO 계약 변경은 없음(순수 additive).**
- `pnpm openapi-ts` 재생성: generated/ 4파일 갱신(+303/-5, 삭제분은 import/export 줄 재배열).
- `pnpm typecheck`: 전 패키지 통과 — 기존 목(entities/*)–명세 불일치 없음.
- **판정**: 명세 드리프트가 additive뿐이므로, 기존 화면의 "응답 안 뜸"의 원인 후보에서 **계약 불일치는 제외될 가능성이 높다**. 남는 후보는 클라이언트(모바일 코드) 아니면 서버다. 단, 개별 실패 건의 분류는 실측에서 개별 확정한다.
- 신규 2개 엔드포인트는 현 모바일 화면 어디에서도 호출하지 않는다(코스 화면은 missions API 4종 사용) — 이번 점검 범위에 영향 없음.
- 스냅샷+생성물(현재 워킹트리 unstaged 5파일)은 이 브랜치에서 함께 커밋한다(CI 드리프트 검사 대응).

1. 판정표 완성이 항상 우선. 수정하다 판정표가 미완이 되면 안 된다.

## 추정 및 질문 — 전건 사용자 확정 (2026-08-24)

- **[확정 1]** 조회 실패 유도 = "기기 네트워크 차단" 표준화 — **승인. 실패 유도 실행한다.** 무선 adb가 같이 끊기는 구간은 USB 수행.
- **[확정 2]** **신고(내 영상 관리)**: **(a) 실제 신고 POST를 발사한다** — 사용자 승인. 실 서버에 신고 레코드가 남는 점을 판정표에 기록.
- **[확정 3]** mutation은 점검 직후 원복. **프로필 이미지 삭제(DELETE)는 실제 실행 승인** — 원복 API가 없어 미복구 상태로 남아도 된다(사용자 확인).
- **[확정 4]** 테스트 영상 실 업로드 **무제한 승인** — 업로드 점검에서 생성, 내 영상 관리 삭제 점검에서 정리.
- **[확정 5]** 실 카카오 로그인이 기본, `use-dev-login` 폴백 사용 가능. **단, dev-login은 개발 전용이며 배포(프로덕션)에서는 제거되어야 한다**(사용자 명시) — 사용 시 실 카카오 경로와의 차이(토큰 발급 주체·신규 가입 분기 미경유)를 판정표에 명시하고, **dev-login 경로가 프로덕션 빌드에 노출되지 않는지(dev 가드 존재 여부)를 점검 항목으로 겸사 확인해 판정표에 기록한다.**
- **[추정 6]** MSG-446 영상 재생 화면(`/video/[videoId]`)은 티켓의 7개 화면군에 없다. 시트 카드 탭 시 자연히 경유되므로 관찰 결과는 부수 기록하되, 판정표의 정식 행으로 넣지 않는다.

### 진입 지도 지연 — 원인 규명과 처리

**증상**: 앱 진입 후 UI는 다 떠 있는데 지도 자리만 네이버 SDK의 빈 격자 플레이스홀더로 1~2초 남는다.

**계측**(화면 녹화 20fps 프레임 분석 + 화면 내 타임스탬프 오버레이 — `console.log`가 Metro·logcat 어느 쪽으로도 나오지 않아 렌더를 채널로 썼다):

| 마크 | 시각 |
|---|---|
| 지도 홈 마운트 | 718ms |
| `onInitialized` | 1016ms |
| 첫 카메라 이벤트 → 격자선 45칸 파생 | 1018ms (초기화 **+2ms**) |
| 점령 오버레이 데이터 도착 | 1192ms (+176ms) |
| **실제 타일 페인트** | **~10800ms** |

즉 **우리 JS 파이프라인은 병목이 아니다.** 원인은 SDK의 타일 로딩이고, `onInitialized`는 네이티브 `getMapAsync` 콜백(= 지도 **객체** 생성)에 물려 있어 타일보다 1.5~2초 빠르다 — 이 이벤트에 스플래시를 걸면 "지도 없는 완성 화면"이 그대로 노출된다(증적: `b2_t9800.jpg` — 스플래시가 걷힌 1초 뒤인데 시트·격자선은 다 있고 지도만 비어 있다).

**처리**: 진입 스플래시를 **타일 첫 표시 + 점령 조회 완료**까지 유지한다.
- `shared/splash-gate.ts` — 순수 게이트(멱등 해제 · 상한 타이머 · 중복 대기 방지), vitest 7건. 네이티브 결합은 `shared/splash.ts` 어댑터가 맡는다(`navigation.ts`와 같은 RN 경계 규칙).
- 진입점(`app/index.tsx`)은 목적지가 지도 홈일 때만 붙잡고, 지도 없는 목적지(온보딩·업로드 이어가기)는 즉시 내린다.
- 해제 조건은 `mapReady && occupied.isResolved`. **상한 2.5초**가 안전망이라 오프라인·조회 실패·SDK 로딩 실패에도 스플래시에 갇히지 않는다.

**래퍼 패치가 필요했던 이유**: 타일 첫 표시를 알리는 신호는 네이버 Android SDK의 `NaverMap.OnLoadListener`("지도의 데이터가 모두 로딩되어 최초로 화면에 나타나면", 1회 발화)인데, `@mj-studio/react-native-naver-map` 2.9.0(최신)은 android·ios 어디에서도 이걸 등록하지 않아 JS로 노출되지 않는다. `patches/@mj-studio__react-native-naver-map@2.9.0.patch`로 4곳을 더했다: 이벤트 클래스(`NaverMapLoadedEvent`, `topLoaded`) · `RNCNaverMapView.kt`의 `addOnLoadListener` 등록 · 매니저의 `registerDirectEvent` · codegen 스펙과 JS 래퍼의 `onLoaded` prop. **네이티브 변경이라 `expo prebuild` + APK 재빌드가 필요하고, 래퍼 버전업 때마다 패치 유지가 필요하다.**

기각한 대안: ① `onInitialized` + 고정 지연 — 임의 상수라 기기·네트워크에 따라 빗나간다. ② 진입 뷰포트를 마운트 시점에 자체 추정해 쿼리를 앞당기기 — 계측상 격자선은 이미 초기화 +2ms라 이득이 없고 쿼리 키가 갈려 요청만 2배가 된다. ③ 지도 영역에 자체 플레이스홀더 — 팝인을 다른 팝인으로 바꿀 뿐이다.

**플랫폼 범위 (codex 리뷰 P2 반영)**: 패치는 현재 **Android만** 덮는다. iOS에는 대응 네이티브 리스너가 없어 `onLoaded`가 영영 오지 않으므로, iOS만 `onInitialized`로 폴백시켜 종전 동작을 유지한다(`Platform.OS` 분기). 그렇게 하지 않으면 iOS 진입마다 스플래시가 상한 2.5초를 통째로 기다린다. iOS도 타일 기준으로 맞추려면 래퍼 iOS 패치가 선행돼야 하며 후속 대상이다.

**측정 환경 주의**: 기기가 핫스팟이고 dev 번들이라 타일 fetch·부팅이 실제보다 느리다. Wi-Fi·릴리스 빌드에서는 절대값이 줄어든다(구조는 동일).
