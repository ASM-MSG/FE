# MSG-419: [모바일] API 기반 이식 — 생성 SDK 공유·RN Ky 어댑터·Query Provider·토큰 저장소

## 기획 요약

apps/mobile에는 API 스택이 전무하다(react-query·ky·hey-api 생성물 없음, 화면 20여 개가 mock-* 동작). 웹의 hey-api 생성 SDK를 재생성 없이 공유하고, RN용 Ky 인스턴스·봉투 언랩·에러 인터셉터·인증 파이프라인(토큰 저장/401 재발급 1회)·QueryProvider를 이식해, 이후 모바일 실연동 티켓 전체(MSG-422~431)가 그대로 쓸 배선을 깐다. 개별 화면 연동은 범위 밖 — 기반과 기반이 동작함을 증명할 최소 검증까지만.

## 코드베이스 현황 (스펙 근거)

- **웹 정본 6모듈** (`apps/web/src/shared/api/`): `http-client`(Ky — throwHttpErrors:false·retry:0·credentials:include·auth 훅), `client-config`(`import.meta.env.VITE_API_BASE_URL` 가드 throw + fetch:Ky 주입), `auth-pipeline`(Bearer 주입·X-Device-Id·401 single-flight 재발급·raw fetch 1회 재시도), `envelope`(순수 1함수), `api-error`(순수 — ApiError·normalizeApiError·shouldRetryQuery), `error-interceptor`(generated client 값에 정규화 등록). envelope·api-error는 **import 0의 순수 모듈**, 나머지는 웹 전용 API(localStorage·import.meta.env)에 결합.
- **생성물 결합 구조(핵심)**: `generated/client.gen.ts`가 `'../client-config'`를 **정적 import**한다. 즉 모바일이 generated를 그대로 import하면 웹 client-config → 웹 http-client → 웹 auth-pipeline → `shared/storage`(localStorage) 체인이 딸려 온다. 런타임에서 이 지점을 모바일 구현으로 치환해야 한다.
- **서버의 앱 클라이언트 규약(생성 타입 실측)**: `types.gen.ts`에 `X-Client-Type` 헤더가 reissue·로그인 계열에 존재하고, 주석이 "앱(X-Client-Type: app)만 refreshToken 값이 채워지고 웹은 HttpOnly 쿠키" / reissue body에 `refreshToken?: string`("앱 클라이언트의 리프레시 토큰")을 명시한다 → 모바일은 쿠키 없이 **body/응답 필드로 리프레시 토큰을 주고받는 규약이 이미 명세에 있다**.
- **apps/mobile 현황**: Expo 57 + expo-router(Stack, `_layout.tsx` 6줄) + NativeWind. deps에 react-query·ky 없음, AsyncStorage 있음. `features/auth`는 카카오 로그인 **스텁**(`startKakaoLogin` no-op)과 `/login` 라우트(진입 연결 없음, 딥링크 검증 선례). vitest는 순수 모델 한정(MSG-292 확정 — RN 렌더 테스트 인프라 없음), 웹 원본 대조는 **복제 + parity 테스트** 선례(`format.parity.test.ts`, vitest alias `@`→웹 src). metro.config는 watchFolders에 워크스페이스 루트 포함(크로스 앱 파일 해석 가능).
- **웹 앱층 선례**: `QueryProvider`(staleTime 30s·retry는 `shouldRetryQuery` — 네트워크·5xx만 2회), `configure-auth.ts`(부트스트랩 1회 콜백 주입 — 세션 만료 시 **토큰만 클리어**, 익명 401 남발 때문에 모달을 열지 않는 MSG-325 교훈).
- **웹 auth-store**: 팩토리 + persist(accessToken만, isAuthenticated는 유도) — 모바일 이식의 원형.

## 승인 결과 (2026-08-18, 사용자)

- **질문 1 — 토큰 저장소: `expo-secure-store` 채택 (확정).** iOS Keychain / Android Keystore 암호화 저장으로 티켓 문언("기기 보안 저장소")을 충족한다. 네이티브 모듈이므로 dev client 재빌드(`expo run:ios`)가 검증 전제이며, 재빌드가 불가하면 스모크를 "확인불가"로 남기고 자동 게이트로 진행한다. 어댑터(`shared/token-storage.ts`) 경계 뒤에 격리해 교체 가능성을 남긴다. deviceId 등 비밀 아닌 값은 AsyncStorage 유지.
- **추정 2~6: 전부 승인.** 익명 401 무개입(웹 MSG-325 교훈), 공유 경계 규칙(generated 직접 import / 수기 모듈 복제+parity), dev 스모크 화면 신설·존치, dev social-login으로 로그인 검증, `EXPO_PUBLIC_API_BASE_URL` 폴백 없는 가드 throw — 모두 웹 선례에 근거가 있어 그대로 간다.
- **브랜치**: `feat/mobile-api-foundation`(사용자 생성 정본, 하네스 임의 생성 아님), target `develop` — `sc worktree status`로 확인.

## 추정 및 질문

1. **[질문 1 — 토큰 저장소 선택] → 해결됨: expo-secure-store** (위 승인 결과 참조). 대안 AsyncStorage(평문, 재빌드 불요)는 티켓 문언 미충족으로 기각.
2. **[추정 — 익명 401 무개입]** 티켓은 "401 시 재발급 1회, 실패 시 로그인 화면"만 명시. 문언 그대로면 비로그인 상태의 모든 401(웹에서 지도 조회 등이 익명 401을 상시 냄)이 로그인 화면 강제 이동을 유발한다. 웹 MSG-325에서 같은 문제로 "세션 만료 시 토큰만 클리어" 설계를 채택한 교훈을 이식해, **저장 refreshToken이 있을 때만** 재발급·만료 처리를 수행(AC 8). 확인 필요.
3. **[추정 — 공유 경계 규칙]** generated(기계 생성물)는 크로스 앱 **직접 import**(티켓 명시 — 재생성 금지), 수기 모듈(envelope·api-error·auth-pipeline)은 **복제 + parity 테스트**(모바일 기존 선례 — 웹 파일 이동 시 번들이 아니라 테스트가 깨지도록). 수기 모듈까지 직접 import하는 대안은 웹 리팩터링 여파가 모바일 런타임에 직결되어 기각.
4. **[추정 — dev 스모크 화면 신설·존치]** 개별 화면 연동이 범위 밖이므로 "기반이 동작함"의 관찰 지점으로 `/dev/api-smoke`를 신설하고, 이후 모바일 실연동 티켓들의 디버그 용도로 **존치**한다(프로덕션 진입 연결 없음). 검증 후 삭제를 원하면 알려달라.
5. **[추정 — dev social-login 사용]** 카카오 OAuth 실연동은 이 티켓 범위 밖(모바일 kakao-login은 스텁)이므로, "로그인 성공 시 토큰 저장"(AC 5)의 검증은 웹 DevLoginPanel 선례인 `POST /api/auth/dev/social-login`(X-Client-Type: app)으로 수행한다.
6. **[추정 — baseUrl env]** `EXPO_PUBLIC_API_BASE_URL`(웹 VITE_API_BASE_URL 대응)을 `.env` 계열로 주입, 값은 `https://api.fillmap.kr`. 웹과 동일하게 코드 폴백 없이 미설정 throw.

## 리스크

1. **ky 2.x의 RN 호환 미확증(최대 리스크)** — ky는 브라우저/Node 대상이고 RN은 공식 지원이 아니다. 파이프라인이 쓰는 `Request.clone()`·`new URL(request.url)`·AbortController가 RN(whatwg-fetch 폴리필 + Hermes) 위에서 전부 성립하는지 실기 확증이 없다. 구현 초반에 스모크로 조기 확인하고, 비호환 판명 시 동일 훅 규약(beforeRequest/afterResponse)의 얇은 fetch 래퍼로 대체하는 폴백을 사용자 보고 후 결정한다 — "RN Ky 어댑터"라는 티켓 문언이 있으므로 무단 대체하지 않는다.
2. **웹 client-config의 typecheck 딸림** — Metro는 런타임 해석을 치환하지만 TS는 상대 import(`'../client-config'`)를 치환할 수 없어, 웹 client-config(import.meta.env)·http-client·auth-pipeline·storage(localStorage — DOM lib)가 모바일 TS 프로그램에 포함된다. expo tsconfig.base의 lib 구성(이 워크트리는 미설치라 미확인)에 따라 ambient 선언 보정이 필요할 수 있다. 구현 중 실측해 최소 보정으로 해소하고 작업 로그에 기록.
3. **X-Client-Type: app 실서버 미실측** — 생성 타입(명세)은 app 규약을 명시하지만, dev social-login·reissue가 실제로 refreshToken을 body로 채워 주는지는 실측 전이다. 스모크에서 최우선 확인하고, 명세-실서버 불일치 시 백엔드 환류.
4. **expo-secure-store 값 크기 제한(2KB 권고)** — JWT가 2KB를 넘으면 저장 실패 가능. 실토큰 길이를 스모크에서 확인.
5. **Metro resolveRequest 커스터마이즈** — NativeWind·Storybook 래퍼가 이미 config를 감싸고 있어 resolver 확장과의 공존을 확인해야 한다(스토리북 구동 회귀 확인 포함).
6. **generated 드리프트 게이트** — 이 티켓은 재생성하지 않으므로 openapi-ts 드리프트 검사에 영향 없음(웹 무수정이 곧 게이트 통과 조건).
7. **Figma 분석 생략** — 티켓에 Figma 링크 없음(기반 티켓, UI 없음). 디자인 대조는 검증 대상 아님.
8. **Figma 오탐 방지**: 없음 (대조 대상 없음).

## 커밋 전 리뷰가 잡은 결함 (재작업 2회차 — codex)

**로그아웃 이후 늦게 도착한 재발급이 세션을 되살렸다.** 재발급이 in-flight인 동안 사용자가 로그아웃하면
`onTokensIssued`가 무조건 호출돼 `setTokens`가 accessToken을 다시 채우고(→ `isAuthenticated` 재계산)
회전 토큰을 secure-store에 재기록했다. 로그아웃 후 **다른 계정으로 재로그인**한 경우엔 더 나빠서,
옛 발급분이 새 세션을 덮어쓴 뒤 그 토큰의 재시도가 401을 받아 **새 세션까지 만료 처리**됐다(테스트로 실측).
부수 결함: `void store.setTokens(tokens)`가 fire-and-forget이라 보안 저장소 쓰기 실패가 삼켜져,
회전된 refreshToken이 디스크에 없는 채로 재시도가 진행되고 앱 재시작 시 세션이 끊겼다.

수정: **세션 세대(generation)** 도입 — 스토어가 세대를 소유하고 `logout()`(세션 만료 처리 포함)이 증가시킨다.
파이프라인은 재발급 시작 시점 세대를 캡처해 완료 시점에 대조하고, 다르면 결과를 **폐기**한다(만료 처리도 재시도도 없음
— "실패"와 구분되는 `discarded` 상태). `onTokensIssued`는 `Promise<void>`가 되어 파이프라인이 저장 완료까지 await하며,
저장 실패는 재발급 실패로 취급한다(AC 6의 "회전 토큰 갱신 저장"은 저장 성공까지가 요건). 그에 맞춰
`token-storage.saveTokens`만 실패를 전파하도록 바꿨다(읽기·삭제·deviceId는 총함수 유지).
진행 중 재발급이 옛 세대의 것이면 single-flight 락에 편승하지 않고 새로 시작한다(= 로그아웃의 in-flight 무효화).
회귀 4케이스는 `configure-auth.test.ts`의 "세션 세대" 블록에 있다.

## 스모크가 드러낸 함정 (기록 — 이후 모바일 티켓에 그대로 적용)

**번들 출처 오염.** 메인 레포(`/Users/ho/fillmap/FE`)의 metro가 8081을 점유한 상태에서 워크트리 앱을 띄우면,
dev client가 **메인 레포 번들을 로드한다.** 8082로 metro를 따로 띄우고 `fillmap://expo-development-client/?url=...`
딥링크로 지정해도, `adb reverse`를 재매핑해도, `pm clear`로 앱 데이터를 지워도 소용없었다 — dev client가 계속 8081로 복귀했다.
겉으로는 앱이 멀쩡히 뜨기 때문에 **오염을 알아채지 못한 채 남의 코드를 검증할 수 있다.**
판별법은 그 워크트리에만 있는 라우트를 딥링크로 여는 것이다(여기서는 `fillmap://dev/api-smoke` → "Unmatched Route"면 오염).
확실한 해소는 8081을 점유한 metro를 종료하고 검증 대상 워크트리의 metro를 8081에 올리는 것뿐이었다.
