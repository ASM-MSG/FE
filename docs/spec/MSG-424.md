# MSG-424: [모바일] 업로드 플로우 개편 — 분석 로딩·AI 추천 3개·미리보기·완료 안내 + 업로드 API

> **개정 이력**
> - r1 (초안): 조사 + 질문 6건 제시
> - r2: 사용자 결정 4건(D1~D4) 반영. D4(점령 격자 연동 흡수) 결정에 따라 Phase 0(EPSG:5179 마이그레이션) 신설
> - **r3 (현재)**: **D4 철회.** 점령 격자 실연동이 병렬 진행 중인 **MSG-423의 범위**임이 확인돼(오케스트레이터 지라 조회) Phase 0·E그룹 기준·관련 리스크를 전부 제거했다.
>   `entities/cell`·`features/map-home`은 **한 파일도 건드리지 않는다**. 요구 9는 "무효화 발사"까지를 기준으로 삼고 화면 반영은 MSG-423 머지 후 자연 충족된다.
>   지라 MCP 원본 대조 완료(내용 일치 — `00_ticket.md` 상단 기록).

## 기획 요약

apps/mobile 업로드 플로우를 mock 4단계(선택 → 하이라이트 → 블러 확인 → 미리보기)에서 실 API 기반 4단계(선택 → **분석 중 로딩** → AI 하이라이트 추천 → 미리보기 → **완료 안내**)로 개편한다. 블러는 업로드 후처리로 빠지므로 `/upload/blur` 확인 스텝이 플로우에서 제거되고, 대신 완료 화면이 "잠시 후 AI가 블러 처리를 마치면 알림으로 알려드릴게요"를 안내한다. 웹 MSG-329가 확립한 `presign → S3 PUT → 확정` 계약과 순수 모델 5종을 모바일로 포팅하고, 파일 접근(expo-image-picker)·S3 PUT(전역 fetch)·영속화(AsyncStorage)만 플랫폼별로 갈린다.

**범위 경계**: 지도(`features/map-home`)와 격자 좌표계(`entities/cell`)는 **이 티켓이 건드리지 않는다** — 병렬 MSG-423 소관(D4 참조).

**갈리는 지점 (RN 전용 신규 구현)**
- 파일 접근: 웹 `File`/`URL.createObjectURL`/`use-video-duration` → RN `expo-image-picker` 결과 `{uri, duration(ms), fileName, fileSize, mimeType}`. 길이 실측이 picker 응답으로 오므로 웹 `use-video-duration`은 포팅 불필요.
- S3 PUT: 웹 `api/s3-upload.ts`는 전역 `fetch(uploadUrl, {method:"PUT", body: Blob})`. **`expo-file-system` 미설치 확인**(`require.resolve` 실패) → `await (await fetch(fileUri)).blob()` 후 동일 PUT. **httpClient(ky) 미경유 원칙 유지**(Authorization·X-Client-Type 헤더가 외부 S3로 새는 것 차단 — 웹 B10 취지).
- 트리밍: 웹 `api/ffmpeg-trim.ts`·`model/video-trim.ts` → **포팅하지 않는다**(D1).
- 영속화: 웹 `shared/storage.ts`(동기 localStorage) → AsyncStorage(비동기). `features/onboarding/model/onboarding-storage.ts`의 총함수 패턴을 따른다.

### 서버 계약 확인 (OpenAPI `apps/web/openapi/api-docs.json` + 생성 타입 전수 확인)

- ✅ `POST /api/videos/presigned-url` — `{extension, contentType, contentLength, purpose?}` → `{uploadUrl, s3Key, expiresInSec}`.
- ✅ `POST /api/videos/highlight-preview` — `{s3Key}` → `{highlights: number[][]}`. 명세 원문: **"최대 3구간, 배열 순서가 추천 우선순위, 각 구간 5초 이상… 조건 충족 구간이 없으면 빈 배열"** → 요구 3("최대 3개")은 서버가 이미 보장.
- ✅ `POST /api/videos` — `{s3Key, lat, lng, durationSec(1~30), recordedAt, visibility?}` → `{videoId, gridId, processingStatus, occupied, newBadges, completedMissions, zoneName, …}`.
- ✅ `GET /api/regions/reverse-geocode` — 위치 라벨(`regionName`).
- ❌ **AI 추천의 "선정 사유" 필드·엔드포인트 없음** — `HighlightPreviewResponseDto`는 `highlights: number[][]`뿐. → D2, 환류 F2.
- ❌ **업로드 확정 body에 구간(start/end) 필드 없음** — `startSec`·`endSec`·`trim*`·`segment` 전수 grep 0건. → D1, 환류 F1.

**무효화 키 정합 확인** (D4 철회 후에도 유효한 접점): 생성 `createQueryKey`는 키의 첫 원소를 `{_id, baseUrl, query, …}` 객체로 만들고 무한 쿼리에만 `_infinite: true`를 **추가**한다. 웹 `invalidateGridQueries`는 `[{_id: occupiedKey._id}]` 부분 키로 무효화하므로, TanStack 부분 일치 규칙상 **표준 쿼리와 무한 쿼리 모두에 매칭된다**. MSG-423이 웹처럼 `getOccupiedInViewportInfiniteOptions`(무한 쿼리)를 쓰더라도 이 티켓이 이식하는 무효화가 그대로 걸린다.

### D1 — 확정 body의 `durationSec` = 선택 구간 길이 (구 Q1)

**결정**: 원본 파일을 트리밍 없이 그대로 업로드하되, `POST /api/videos`의 `durationSec`은 **선택 구간 길이**(`end - start`)를 보낸다.

**근거**: 웹 `use-upload-wizard.ts:257`이 `Math.min(30, Math.max(1, Math.round(trim.durationSec)))`로 **트리밍된 구간 길이**를 보낸다 — 원본 길이가 아니다. 모바일도 같은 의미를 유지한다. `highlight-selection`이 구간을 5~28초로 이미 보장하므로 서버 제약(1~30)을 항상 만족해 400이 나지 않는다.

**기각한 대안**: "원본 길이를 1~30으로 clamp" — 30초 초과 영상에서 길이를 거짓 보고하게 되고, 30초로 잘린 값이 실제 영상과 무관해진다.

**남는 불일치(의도적)**: S3의 실제 파일 길이 ≠ 서버 기록 `durationSec`, 그리고 선택 구간이 서버에 전달되지 않는다. → **리스크 R1 유지 + 환류 F1**. 확정 호출부 코드에 환류 대기 주석을 남긴다.

**파생**: 파일 제약 문구를 실 계약에 맞춰 **"최대 180초 · MP4, MOV · 500MB 이하"**로 정정한다(현행 "최대 30초"는 원본 상한을 잘못 안내).

### D2 — 추천 행에 선정 사유를 표시하지 않는다 (구 Q2)

**결정**: 시간 범위만 표시. 사유 텍스트 행을 렌더하지 않고, 순위 라벨도 넣지 않는다. `mock-segments.ts`의 사유 문구("움직임·밝기 지속" 등)는 삭제된다.

**근거**: 서버 `HighlightPreviewResponseDto`는 `highlights: number[][]`뿐이라 사유를 계산하지 않는다. 웹이 같은 상황에서 이미 "사유 라벨 없음"을 확정했고(MSG-329 티켓 13, `highlight-selection.ts` 주석: "Figma 사유 문구는 플레이스홀더"), 플랫폼 간 표시를 통일한다.

**기각한 대안**: ① 순위 라벨("AI 추천 1순위") — 서버가 순서를 우선순위로 보장하므로 허위는 아니나 웹과 갈라진다 ② mock 문구 존치 — 서버가 계산하지 않은 근거를 사실인 양 제시하게 되어 부적절.

**티켓 요구 4의 "선정 사유"는 의도적 미이행**이다 → **환류 F2**.

### D3 — 실 영상 프리뷰 + 구간 시작 seek (구 Q3)

**결정**: `expo-video`(~57.0.2)를 도입한다. 하이라이트·미리보기 프리뷰 영역에 선택 영상을 실제 렌더하고, 추천 행 재생 버튼 = 해당 구간 시작 시각으로 seek + 재생. **구간 끝 자동 정지·반복은 범위 밖.**

**근거 + 리스크 해소**: `expo-video`는 이미 `apps/mobile/package.json` 의존성이며, **`features/upload/ui/blur-preview.tsx`가 이미 `VideoView`·`useVideoPlayer`를 사용 중**임을 확인했다. 즉 네이티브 모듈이 **현재 dev client에 이미 포함**돼 있어 **재빌드가 필요 없다**. (r1에서 리스크로 올렸던 항목이 조사로 해소됐다.)

**파생**: Figma의 점선 회색 플레이스홀더는 재현하지 않는다(오탐 방지 5).

### D4 — 점령 격자 연동은 MSG-423 소관 (**철회됨**)

**경위**: r2에서 요구 9("업로드한 격자가 채워진 상태로 반영")를 온전히 충족하기 위해 점령 격자 실연동을 이 티켓이 흡수하기로 했다가, **r3에서 철회했다.**

**흡수 검토 시 확인한 사실** (기록 보존 — 나중에 왜 안 했는지 추적용):
- 웹 조회 경로: `features/map-home/model/use-occupied-grids-query.ts`(`getOccupiedInViewportInfiniteOptions` + 커서 페이지네이션 + 비로그인 게이트) → `model/occupied-grid-overlay.ts`(`decodeGridIndex` → `cellCornersAt`). 훅·파생 모두 지도 SDK 무의존이라 이식 자체는 가능하다.
- **좌표계 불일치**: 웹은 MSG-347/357에서 EPSG:5179로 전환했으나 모바일 `entities/cell/model/grid.ts`는 MSG-325의 구 위경도 근사(원점 0,0 · 0.0009°/0.00115° 스텝 · `{col,row}` · 2점 Bounds)에 머물러 있다. `grid.parity.test.ts`가 이 상태를 *"모바일 5179 마이그레이션은 별도 티켓 — MSG-357 후속 항목"*으로 명시하고 동등성 단정을 의도적으로 해제해 뒀다. 서버 `gridId`가 5179 인덱스라 구 체계로는 디코드가 불가능하며, 흡수하려면 `entities/cell` 2개 + `features/map-home` 8개 + `features/grid-detail` 3개 + 테스트 8개 ≈ 20파일의 마이그레이션이 선행돼야 했다.

**철회 사유**: 오케스트레이터가 지라를 조회한 결과 **점령 격자 실연동은 병렬 워크트리에서 동시에 진행 중인 MSG-423의 범위**였다 — "[모바일] 지도 홈 시트 1열 전환·상단 칩 UI 개편 + **격자/영상 조회 연동**", 포팅 대상에 `grid-overlay`·`occupied-grid-overlay`·`cell-viewport`·`viewport-query`·`viewport-store` 포함, 티켓 원문에 *"충돌 주의: `map-home-screen.tsx`를 공유 — 이 티켓이 먼저 머지된다"* 명시. MSG-424가 흡수하면 같은 작업을 두 세션이 동시에 수행해 `entities/cell`·`features/map-home`에서 대규모 충돌이 난다. **사용자가 철회를 승인했다.**

**결과**: MSG-424는 `entities/cell`·`features/map-home` 어느 파일도 수정하지 않는다(수용 기준 41). 요구 9는 **무효화 발사까지**(기준 28) + **홈 복귀 동선**(기준 29)을 이 티켓의 기준으로 삼고, 화면 반영은 MSG-423 머지 후 자연 충족된다(리스크 R2). 두 티켓의 접점은 `invalidateGridQueries`의 쿼리 키 하나뿐이다.

### D5 — 슬라이더는 기존 의존성으로 자체 구현 (구 Q4, 이의 없음)

`range-slider-static.tsx`는 확인 결과 완전한 정적 View 조합(핸들 15%/72% 하드코딩, 드래그 불가)이다. 요구 5는 실 드래그를 요구하므로 `react-native-gesture-handler`(~2.32.0) + `react-native-reanimated`(4.5.1) — 둘 다 이미 mobile 의존성 — 으로 자체 구현한다. `@react-native-community/slider`는 단일 핸들이라 범위 슬라이더에 부적합. **새 의존성 추가 없음.**

### D6 — 완료 화면은 미리보기의 전면 오버레이 (구 Q5, 이의 없음)

라우트로 만들면 하드웨어 뒤로가기가 미리보기로 돌아가 이미 확정된 업로드를 재게시할 수 있다. 미리보기 화면이 `completed` 상태에서 전면 오버레이로 렌더한다(웹 `useUploadWizard.completed` 미러). 시각 결과는 Figma 전면 화면과 동일.

### D7 — 진행 바는 경과 시간 기반 의사 진행률 (구 Q6, 이의 없음)

`highlight-preview`는 동기 API라 진행률 정보를 주지 않는다. 웹은 이 때문에 확정형 진행 바를 의도적으로 버렸으나(`AnalyzingModal.tsx` 주석), **MSG-424 티켓은 진행 바와 예상 소요 시간을 명시적으로 요구**하므로 티켓 요구를 우선한다. 경과 시간 기반 점근 곡선(응답 전 100% 미도달)으로 구현하고 "보통 10~20초 정도 걸려요"는 Figma 문구 그대로 쓴다. **웹과 의도적으로 달라지는 지점**이므로 검증에서 웹 대조로 결함 판정하지 않는다.

### D8 — 확정 좌표는 `resolveMapCenter()` (구 A4, 이의 없음)

웹은 지도 뷰포트 중심(결정 A)을 쓰지만 모바일에는 뷰포트 스토어가 없다(MSG-423이 `viewport-store`를 도입 중이나 이 티켓은 의존하지 않는다). `shared/geolocation.resolveMapCenter()`(현재 위치, 실패 시 서면 폴백)를 좌표 정본으로 삼는다 — 티켓 문구("지금 위치의 격자에 순간을 기록하세요")에 부합.

### D9 — `processing-poll`은 모델만 포팅 (구 A7, 이의 없음)

요구 11을 **업로드 플로우(선택~확정) 진행 상태**로 해석해 AsyncStorage 영속을 구현한다. 확정 이후 서버 블러 처리 대기(웹 `pendingVideoStorage` + `use-processing-watcher` + 완료 통지)는 티켓 제외 범위("블러 결과 확인 화면과 완료 알림 수신은 MSG-429")이므로 **모델만 포팅**하고 워처·저장소·통지 UI는 만들지 않는다.

## 리스크

### R1 — 선택한 구간이 서버에 도달하지 않는다 (D1로 완화, 잔존)

D1로 400 위험은 제거됐지만(항상 5~28초 전송), 구간 선택이 업로드 결과에 반영되지 않는 구조적 공백은 남는다. 사용자에게는 "구간을 고르는 행위"로 보이지만 서버는 원본 전체를 받는다. **환류 F1이 해소될 때까지 이 화면의 절반은 선행 UI**다. 검증 시 "구간을 바꿔도 결과 영상이 같다"를 결함으로 판정하지 않는다.

### R2 — 요구 9의 화면 반영이 MSG-423에 의존한다 (r2의 "규모 팽창" 리스크를 대체)

D4 철회로 **이 티켓만으로는 "홈 복귀 후 격자가 채워져 보인다"를 관찰할 수 없다.** 모바일 지도의 점령 격자가 여전히 `MOCK_OCCUPIED_CELLS` 하드코딩이기 때문이다.

- **검증 영향**: 수용 기준 28은 vitest로 무효화 발사만 확인하고, 기준 29는 홈 복귀 동선까지만 확인한다. **화면상 격자 채움은 이 티켓의 검증 대상이 아니다** — page-verifier가 이를 미충족으로 판정하지 않도록 명시한다.
- **접점 관리**: 두 티켓이 만나는 지점은 `invalidateGridQueries`의 쿼리 키 하나다. 생성 `createQueryKey`가 무한 쿼리에만 `_infinite: true`를 **추가**하고, 웹 무효화가 `[{_id}]` 부분 키를 쓰므로 **MSG-423이 무한 쿼리를 쓰더라도 매칭된다**(실측 확인). 키 팩토리를 웹 그대로 쓰는 한 조율 실패 위험은 낮다.
- **머지 순서**: MSG-423 티켓 원문이 "이 티켓이 먼저 머지된다"고 명시했다. MSG-424가 먼저 머지되면 무효화가 잠시 no-op으로 남을 뿐 회귀는 없다.
- **후속 확인**: MSG-423 머지 후 업로드 → 홈 복귀 격자 채움을 한 번 교차 검증한다(환류 F3).

### R3 — 원본 500MB를 RN에서 blob으로 올리는 메모리 압박

`expo-file-system` 미설치 확인 → 스트리밍 업로드 경로가 없다. `await (await fetch(fileUri)).blob()`은 파일 전체를 JS 힙에 올린다. D1로 **원본 전체(최대 180초)를 올리게 되어 압박이 r1 상정보다 커졌다**. 완화: ① FE 검증으로 500MB 초과 사전 차단(`isWithinSizeLimit`) ② 실기 검증에 대용량(≥200MB) 케이스 1건 필수 포함 ③ 문제 시 `expo-file-system` 추가(의존성 승인 필요, 네이티브 모듈이라 dev client 재빌드 수반) — 이번엔 검증에서 판정하고 필요 시 후속.

### R4 — `highlight-preview` 응답 지연 vs ky 기본 타임아웃

서버 동기 응답 5~30초(부하 시 3배). 웹은 이 호출에만 타임아웃을 120초로 연장했다(`analysisHttpClient = httpClient.extend({timeout: 120_000})`). 모바일 `http-client`에도 동일 처리가 필요하다 — **빠뜨리면 정상 분석이 항상 타임아웃한다.** 구현 체크리스트 필수 항목.

### R5 — 도달 불가 라우트 `/upload/blur` 존치

플로우에서 빠지지만 파일은 남는다(MSG-429 소유). Expo Router는 파일 존재만으로 라우트를 등록하므로 딥링크·`router.push("/upload/blur")`로는 여전히 열린다. 죽은 화면이 아니라 **다음 티켓 대기 상태**임을 코드 주석으로 남긴다.

### R6 — AsyncStorage 비동기 재수화 vs 화면 첫 렌더

웹 `processing-store.hydrate()`는 동기 localStorage라 즉시 복원된다. AsyncStorage는 비동기이므로 복원 전에 "선택 없음"이 한 프레임 렌더될 수 있다. `token-storage`의 `hydrated` 게이트 패턴으로 복원 완료 전 렌더를 막는다(수용 기준 38).

### R7 — 모바일에는 컴포넌트 렌더 테스트가 없다

`apps/mobile/vitest.config.ts`가 순수 모델만 테스트하도록 못박혀 있다(MSG-292 확정 4). 웹은 `upload-wizard-flow.smoke.test.tsx` 9케이스로 위저드 동작 계약을 고정했지만 모바일에는 대응물이 없다 → **화면 전이·실패 분기의 회귀 안전망이 실기 검증뿐**이다. 완화: 스텝 전이·실패 분기 판정을 최대한 순수 모델(`upload-flow-store`·`upload-wizard`)로 밀어내고 화면은 렌더만 하게 만든다.

### Figma 오탐 방지 (검증에서 결함으로 판정하지 말 것)

### 검증이 잡은 결함 2건 (둘 다 실기에서만 드러남)

1. **S3 PUT 100% 403 `SignatureDoesNotMatch`.** 원인은 자격증명·contentLength가 아니라 **Expo winter fetch가 Blob body일 때 호출자의 `Content-Type`을 blob의 type으로 덮어쓰는 것**(`expo/src/winter/fetch/RequestUtils.ts`). 로컬 파일 읽기 응답에는 content-type이 없어 그 값이 빈 문자열이 됐고, presigned URL이 `X-Amz-SignedHeaders=content-length;content-type;host`라 서명이 어긋났다. `.blob()` → `.arrayBuffer()`로 해소(ArrayBuffer 바디에는 override 규칙 자체가 없다). **웹 원본을 그대로 옮긴 것이 함정** — 브라우저 fetch는 명시 헤더를 우선하므로 같은 코드가 웹에서는 정상이고, vitest 스텁은 플랫폼 fetch 구현 차이를 재현하지 못한다. 이 티켓처럼 웹 모듈을 포팅하는 작업에서 "웹에서 되니 된다"가 성립하지 않는 경계다.
2. **`[업로드하기]` 연타가 서버에 중복 영상을 실제로 생성.** 프록시 실측으로 videoId 287+288 / 289+290을 확인(2/2 재현), 완료 화면은 한 번만 떠서 **사용자가 인지할 수 없었다**. `isPending`은 비동기 상태라 같은 틱 두 번째 탭에 아직 false이고, `mutate()`가 mutationFn을 마이크로태스크로 미루므로 mutationFn 안의 가드도 통과한다 — **가드는 발사 지점에서 동기여야 한다.** 스토어 동기 잠금으로 해소했고, 수정 후 4연타 → presign 1건 · `POST /api/videos` 1건.
