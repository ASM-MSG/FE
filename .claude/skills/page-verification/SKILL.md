# Page Verification — 수용 기준 기반 검증

구현 결과를 스펙(`01_spec.md`)의 수용 기준으로 판정한다. 판정 단위는 항상 개별 기준이다 — "전반적으로 잘 됨"은 검증이 아니다.

**지적 범위 원칙**: 수용 기준·규칙 감사·회귀에 영향을 주는 결함만 실패로 잡는다. 그 밖의 개선 아이디어(리팩터링 여지, 스타일 취향)는 리포트 말미 "참고" 항목으로만 남긴다 — 검증자가 지적을 만들어내기 시작하면 재작업 루프가 과잉 방어 코드로 흐른다.

## 절차

### 1. 자동 검증

```
pnpm test        # apps/web vitest (run 모드)
pnpm typecheck   # 전 패키지 — web(tsc -b) + ui-web(stories 포함 strict) + design-tokens + tailwind-preset
pnpm lint        # 전 패키지 — apps/web + packages/ui-web
```

반드시 루트에서 실행한다 — `--filter web`으로 좁히면 ui-web 승격 산출물(컴포넌트·스토리)이 검사에서 빠진다. 셋 중 하나라도 실패하면 이후 단계를 진행하되, 리포트 최상단에 실패를 명시한다.

스페이싱·사이징 px 임의값, 색상 임의값, RN 경계 규칙(model의 라우터/window 참조)은 eslint가 기계 강제한다 — 이 범위는 lint 통과가 곧 감사 통과다. 단, 변경 파일에 `eslint-disable`이 새로 생겼으면 우회 시도이므로 사유를 검증하고 리포트에 기록한다.

### 2. 규칙 감사 (린터가 못 보는 것만 직접 확인)

빌드 리포트의 주장을 믿지 말고 변경된 파일을 직접 확인한다:

- **재사용 위반**: 페이지/features에 ui-web 컴포넌트와 역할이 겹치는 UI가 새로 만들어지지 않았는지. `packages/ui-web/src/index.ts` 인벤토리와 대조. 재사용하지 않은 결정에는 근거(JSDoc 또는 빌드 리포트)가 있어야 한다
- **린트 범위 밖 px 임의값**: 변경 파일에서 `text-[…px]`·`leading-[…px]`·`border-[…px]`·`ring-[…px]` 신규 사용 확인 — 토큰(`text-fm-*`)·기본 클래스로 대체 가능하면 위반 (린트는 스페이싱·사이징 계열만 잡는다, DESIGN_SYSTEM 1조)
- **FSD 배치**: 신규 UI가 pages/{페이지}/ui vs features/{도메인}/ui 구분 기준(page-implementation 스킬)에 맞게 놓였는지 — 같은 도메인의 model과 UI가 서로 다른 레이어로 갈라지면 위반
- **테스트-기준 매핑**: 로직형 수용 기준마다 대응하는 테스트가 실제로 존재하고, 테스트가 기준의 내용을 검증하는지(이름만 비슷한 빈 테스트가 아닌지) 확인
- **테스트 무결성**: 변경 diff의 테스트 파일을 직접 확인 — (a) 이전 티켓에서 커밋된 테스트·스모크의 단정 약화(`.toEqual`→`.toBeTruthy` 류)·단정 삭제, (b) `test.skip`/`it.skip`/`test.only` 신규 발생, (c) 테스트 파일 삭제(단, 동일 내용의 이동·리네임은 삭제로 보지 않는다), (d) 특정 테스트 입력에만 반응하는 좁은 특수분기가 구현 코드에 생겼는지. 발견 시 현 티켓 스펙에 근거가 있는지 검증하고 없으면 실패 판정 + 사유를 리포트에 기록한다(eslint-disable 감사와 같은 결). 현 티켓 신규 테스트의 품질은 위 테스트-기준 매핑이 담당하므로 중복 지적하지 않으며, test-first 특성상 구현·테스트 간 단순 리터럴 일치(스펙 명시값·mock 수치)는 지적 대상이 아니다

### 3. 실동작 검증 (브라우저)

1. `pnpm dev`로 dev 서버 실행 (백그라운드)
2. 화면형 수용 기준을 하나씩 브라우저에서 재현하고 관찰한다. 브라우저 자동화 도구가 있으면 스크린샷을 `_workspace/MSG-{번호}/screenshots/`에 남기고, 자동화가 불가하면 리포트에 "스크린샷 미보존(사유)"를 명시한다 — 조용히 생략하지 않는다
3. **Figma 대조**: 스펙에 Figma 노드가 있으면 해당 노드 스크린샷(`get_screenshot`)과 렌더 결과를 나란히 놓고 구조·간격·색·타이포를 비교한다. 스펙의 "오탐 방지/의도된 편차" 목록에 있는 차이는 결함이 아니다 — 목록에 없는 차이만 실패 후보로 올린다
4. **a11y 점검** (변경된 UI 범위만):
   - 아이콘 전용 버튼·인터랙티브 요소에 접근 가능한 이름(aria-label 등)이 있는가
   - 키보드만으로 조작 가능한가 (포커스 도달 + Enter/Space 동작, 커스텀 드래그는 대체 수단 유무)
   - Dialog류는 열릴 때 낭독될 제목(Title)이 있는가 (Radix가 포커스 트랩·Esc는 커버하므로 재검증 불필요)
   - 색 대비(4.5:1)는 jsdom에서 검증 불가 — 새 색 조합이 나오면 브라우저 도구나 대비 계산으로 확인하고, 불가하면 확인불가로 분류
5. 기준 외 스모크 확인: 콘솔 에러 없음, 페이지 진입·이탈 정상

### 4. 뷰 스모크 승격 판단

화면 AC 검증을 위해 임시 RTL 렌더 하네스를 작성했다면, 버리기 전에 판단한다: **이 흐름이 이전 티켓에서도 재검증됐거나 앞으로 재검증될 흐름인가?** 그렇다면 하네스를 `src/**/*.smoke.test.tsx`로 정리해 커밋 자산으로 승격한다 (예: 업로드 위저드 스텝 전환). 승격 기준은 안정된 사용자 흐름만 — 자주 바뀌는 문구·스타일 단정은 넣지 않는다. 승격 시 검증 리포트(`03_verify_report.md`)에 기록한다.

> 스모크 승격은 "검증자는 코드를 수정하지 않는다" 원칙의 **명시적 예외**다 — 검증 자산(테스트 파일) 추가만 허용되며, 프로덕션 코드 수정은 여전히 금지(재작업 지시로 page-builder에 전달).

### 5. 리포트 작성

`_workspace/MSG-{번호}/03_verify_report.md`:

```markdown
# MSG-{번호} 검증 리포트

## 자동 검증
| 항목 | 결과 |
|------|------|
| vitest | 통과 (N개) / 실패 |
| typecheck | 통과 / 실패 |
| lint | 통과 / 실패 (신규 eslint-disable 유무) |

## 수용 기준 판정
| # | 기준 | 판정 | 근거 |
|---|------|------|------|
| 1 | {기준} | 통과/실패/확인불가/WAIVED | {관찰한 것 — 실패 시 재현 조건} |

## 규칙 감사
- 재사용: {위반 없음 / 위반 목록(파일:줄)}
- FSD 배치: {...}
- Figma 대조: {일치 / 편차 목록(의도된 편차 제외)}
- a11y: {통과 항목 / 이슈 / 확인불가(색 대비 등)}

## 재작업 지시
{실패 항목별로 무엇을 고쳐야 하는지. 없으면 "없음 — 커밋 가능"}

## 참고 (판정에 영향 없음)
{개선 아이디어, 발견한 죽은 코드 등}
```

## 판정 원칙

- **통과**: 기준을 직접 관찰(테스트 실행 결과 또는 브라우저 재현)로 확인함
- **실패**: 기준과 다른 동작을 관찰함 — 재현 조건을 리포트에 기록
- **확인불가**: 외부 요인(API 미구현, 서버 실행 실패 등)으로 관찰 자체가 불가 — 사유 명시. 확인불가를 실패로 분류하면 불필요한 재작업을, 통과로 분류하면 거짓 완료를 만든다
- **WAIVED**: 실패를 관찰했지만 사용자가 알고 수용하기로 결정함 — 결정 근거와 함께 기록한다. 조용한 통과 처리와 달리 이후 티켓에서 추적 가능하다
- 재검증 시: 이전 실패 항목 우선 확인 + 수정이 다른 기준을 깨지 않았는지 회귀 확인

## 결정 기록

검증에서 테스트가 실제 버그를 잡았거나(자동 검증 실패 → 수정), 규칙 감사에서 위반이 발견되어 고쳐진 경우, `docs/decisions/DECISIONS.md`에 한 줄 기록한다. WAIVED 판정도 결정이므로 기록 대상이다.
